## reborn-chip

### [低] RebornChip：根节点的 `props.class` 被合并了两次
- 位置：`app/components/reborn/ui/reborn-chip/RebornChip.vue:67`、`app/components/reborn/ui/reborn-chip/RebornChip.vue:75`
- 类别：模板
- 依据：`references/reactivity.md`「用 computed 承载可复用的 class 逻辑」——同一份类名只应有一个合并入口
- 现状：
  ```ts
  root: (opts?: { class?: any }) => styles.root({ class: cn(opts?.class, props.class, props.ui?.root) }),
  ```
  ```vue
  <span :class="ui.root({ class: props.class })">
  ```
  `ui.root()` 内部已经并入 `props.class`，模板又把它作为 `opts.class` 传一次。`cn` 会去重，所以目前没有可见差异，但 `opts.class` 排在 `props.ui?.root` 之前，读代码的人很难判断两者谁覆盖谁，以后调整合并顺序时容易出错。
- 改法：模板改成 `:class="ui.root()"`，合并顺序只由 `ui.root` 决定。
- 影响：不改公开 API；UniApp 端 `RebornChip` 不受影响；无回归风险。

## reborn-collapse

### [高] RebornCollapse：v-model 受控时，`toggle` 事件载荷是切换前的旧值
- 位置：`app/components/reborn/ui/reborn-collapse/RebornCollapse.vue:89-93`
- 类别：数据流
- 依据：`references/component-data-flow.md`「需要立刻拿到更新后的值时，用事件里的值」；项目已知坑：受控绑定下 `model.value = x` 之后同步读到的仍是旧值，事件载荷要用本地新值
- 现状：
  ```ts
  function toggle() {
      if (props.disabled) return
      if (collapse.value) { hide() } else { show() }
      emit('toggle', collapse.value)
  }
  ```
  `useModel` 在父组件传了 `v-model` 时，setter 只派发 `update:modelValue`、不改本地值，要等父组件重渲染后 props 回流才变。所以只要用了 `v-model` 再监听 `@toggle`，载荷永远与实际状态相反：展开时收到 `false`，收起时收到 `true`。官方演示 `app/components/reborn/examples/reborn-collapse/RebornCollapseDemo.vue:196-200` 正是 `v-model` + `@toggle` 的写法，回显文案会一直反着显示；文档 `content/2.components/miscellaneous/reborn-collapse.md:98` 写的是「载荷是切换后的状态」。
- 改法：
  ```ts
  function toggle() {
      if (props.disabled) return
      const next = !collapse.value
      collapse.value = next
      emit('toggle', next)
  }
  ```
- 影响：不改公开 API，只修正载荷与文档一致；UniApp 端没有 `toggle` 事件（两端差异表已写明），不需要同步；回归面只有监听 `toggle` 的使用方，其中按旧（错误）值写反逻辑的需要一并检查。

### [低] RebornCollapse：通过 expose 暴露的 `isAnimating` 是可写的内部 ref
- 位置：`app/components/reborn/ui/reborn-collapse/RebornCollapse.vue:37`、`app/components/reborn/ui/reborn-collapse/RebornCollapse.vue:103`
- 类别：数据流
- 依据：`references/composables.md`「状态只允许经由动作修改时，返回 readonly」；`references/component-data-flow.md`「用 defineExpose 只暴露预期的 API」
- 现状：`defineExpose({ show, hide, toggle, resize, isAnimating })` 直接交出组件内部的 `ref`，外部拿到模板引用后可以写 `isAnimating.value = false`，而组件的动画收尾（`:84` 起）和主题里的 `animating` 变体都依赖它，被外部改写后会出现「动画中却撤掉了 `overflow-hidden` / `contain`」的错位状态。
- 改法：`defineExpose({ ..., isAnimating: readonly(isAnimating) })`。`resize()` 是为对齐 UniApp 端同名方法刻意保留的空实现（文档 `reborn-collapse.md:204` 已说明），不属于问题。
- 影响：expose 的类型从 `Ref<boolean>` 变为 `Readonly<Ref<boolean>>`，文档 Expose 表格同步改类型；仓库内没有写入它的调用方（`RebornSticky` 靠 `reborn-collapse__animating` 类名判断，不读这个 ref），回归风险低。

## reborn-color-picker

### [高] RebornColorPickerPanel：透明度改动永远传不到 v-model
- 位置：`app/components/reborn/ui/reborn-color-picker/RebornColorPickerPanel.vue:96`、`app/components/reborn/ui/reborn-color-picker/RebornColorPickerPanel.vue:134-136`、`app/components/reborn/ui/reborn-color-picker/RebornColorPickerPanel.vue:216`
- 类别：数据流
- 依据：SKILL.md「一个数据源，其余派生」；`references/reactivity.md`「副作用放 watcher，派生用 computed」——回传通道不应挂在一个有损的派生值上
- 现状：
  ```ts
  const hexValue = computed(() => hsvaToHex(colorHsv.value));
  watch(hexValue, (val: string) => {
      emit("update:modelValue", val);
  });
  ```
  `@uiw/color-convert` 的 `hsvaToHex` 只输出 `#rrggbb`，不含 alpha（含 alpha 的是 `hsvaToHexa`）。透明度滑块只改 `colorHsv.a`（`:216`），`hexValue` 不变，`watch` 不触发，于是拖透明度滑块、在 rgba 格式下看到的透明度都只停在面板本地，绑定值始终是不透明色；关掉浮层再打开（面板随 `RebornPopover` 重新挂载）透明度也丢了。面板上有一条透明度滑块，用户每次拖它都不生效。
- 改法：把「对外输出的值」定义成包含 alpha 的派生值，并只从交互入口提交（见本目录第三条）：
  ```ts
  const outputValue = computed(() =>
      colorHsv.value.a < 1 ? hsvaToHexa(colorHsv.value) : hsvaToHex(colorHsv.value),
  );
  function commit(next: HsvaColor) {
      colorHsv.value = next;
      emit("update:modelValue", outputValue.value);
  }
  ```
  `watch(() => props.modelValue)` 里的比较对象同步改成 `outputValue`。
- 影响：带透明度时绑定值会从 6 位变成 8 位十六进制，属于对外取值形态的变化，文档要写明；UniApp 端 `packages/uniapp-project/src/components/reborn-color-picker/RebornColorPickerPanel.vue:106-151` 已按 `format` 输出含 alpha 的 rgba 字符串并支持 `update:format`，Web 端更稳妥的做法是对齐 UniApp 的 `format` 能力，否则两端同一个 v-model 的取值形态不一致。

### [高] RebornColorPickerPanel：十六进制输入框边输边被改写，无法手输色值
- 位置：`app/components/reborn/ui/reborn-color-picker/RebornColorPickerPanel.vue:99-125`、`app/components/reborn/ui/reborn-color-picker/RebornColorPickerPanel.vue:279`
- 类别：响应性
- 依据：`references/reactivity.md`「派生值用 computed」的前提是派生可逆；`references/component-data-flow.md`「v-model 只用于真正的双向契约」——输入到一半的文本不是合法值，不应立刻回写
- 现状：
  ```ts
  const displayValue = computed({
      get: () => { if (format.value === "hex") return hexValue.value.toUpperCase(); /* … */ },
      set: (val: string) => { if (val.startsWith("#")) colorHsv.value = hexToHsva(val); /* … */ },
  });
  ```
  ```vue
  <RebornInput v-model="displayValue" size="sm" :class="ui.input()" spellcheck="false" />
  ```
  `RebornInput` 每次 `input` 事件都回写 v-model（`RebornInput.vue:365` 起）。逐字符输入 `#123456` 时：输到 `#12`，`hexToHsva("#12")` 得到 `v: null`，格式化回来是 `#000000`，输入框立刻被改写成 `#000000`；输到 `#123` 被当成三位缩写改写成 `#112233`，再敲的字符接在改写后的文本上。这几个中间值已在本地用 `@uiw/color-convert` 验证。除非粘贴完整色值，手输十六进制基本不可用，而 hex 是默认格式。
- 改法：输入框绑独立的草稿文本，失焦 / 回车且合法时才提交，聚焦期间不被派生值覆盖：

  ```ts
  const draftText = shallowRef(displayValue.value);
  const editing = shallowRef(false);
  watch(displayValue, (v) => { if (!editing.value) draftText.value = v; });
  function commitDraft() {
      editing.value = false;
      const next = parseColor(draftText.value); // 只接受完整的 #rgb / #rrggbb / #rrggbbaa / rgb(a)()
      if (next) commit(next); else draftText.value = displayValue.value;
  }
  ```
  模板：`<RebornInput v-model="draftText" @focus="editing = true" @change="commitDraft" />`（`RebornInput` 失焦时派发 `change`，`RebornInput.vue:420`）。
- 影响：不改公开 API；UniApp 端 `displayValue` 也是可写 computed（UniApp `RebornColorPickerPanel.vue:106-121`），解析函数不同，需单独验证是否有同样的改写；回归点是点预设色块、拖拽后输入框文本仍要同步更新。

### [中] RebornColorPickerPanel：回传挂在 `watch(hexValue)` 上，外部改值会被改写后回传，拖动时每帧派发并触发表单校验
- 位置：`app/components/reborn/ui/reborn-color-picker/RebornColorPickerPanel.vue:128-136`、`app/components/reborn/ui/reborn-color-picker/RebornColorPicker.vue:52-58`
- 类别：数据流
- 依据：`references/component-data-flow.md`「Props 向下、事件向上」——事件应表达用户操作，而不是对 prop 变化的回声；`references/reactivity.md`「watcher 只做副作用」
- 现状：
  ```ts
  watch(() => props.modelValue, (val) => { if (val && val !== hexValue.value) colorHsv.value = hexToHsva(val); });
  watch(hexValue, (val) => { emit("update:modelValue", val); });
  ```
  ```ts
  set: (val: string) => { emit('update:modelValue', val); validate('change') },
  ```
  任何让 `hexValue` 变化的来源都被当成用户操作派发，包括父组件改值：浮层打开时父组件把值设成 `#FF0000`，面板会派发 `#ff0000` 把父组件的值改成小写；设成 `red`、`rgb(…)`、`#f00` 这类非六位十六进制，`hexToHsva` 解析成黑色或别的值后同样回写，父组件的数据被静默篡改。拖拽饱和度 / 色相时每个 `mousemove` 都派发一次，`RebornColorPicker` 的 setter 跟着每帧调用 `validate('change')`，在表单里拖一次会触发几十次字段校验。
- 改法：删掉 `watch(hexValue, emit)`，只在拖拽、点预设、输入提交这几个交互入口调用上一条的 `commit()`；拖拽中照常派发 `update:modelValue` 让预览跟手，校验移到松手时：面板新增松手 / 选定时派发的 `change` 事件，`RebornColorPicker` 在 `@change` 里调 `validate('change')`。
- 影响：面板新增 `change` 事件属于 API 扩展，要写进文档；UniApp 端面板同样用 `watch(displayValue, emit)` 回传（UniApp `RebornColorPickerPanel.vue:149-151`），外层已有 `onChange` 事件（UniApp `RebornColorPicker.vue:102`），两端事件名需先统一再改（Web 用 `change` 更符合 Vue 约定）；回归点是外部改值后面板显示要同步、但不再派发 `update:modelValue`。

### [中] RebornColorPickerPanel：拖拽的 window 监听不随卸载清理、缺少 `touchcancel`，同一段逻辑复制了三份
- 位置：`app/components/reborn/ui/reborn-color-picker/RebornColorPickerPanel.vue:161-176`、`app/components/reborn/ui/reborn-color-picker/RebornColorPickerPanel.vue:191-204`、`app/components/reborn/ui/reborn-color-picker/RebornColorPickerPanel.vue:219-232`
- 类别：生命周期与清理
- 依据：SKILL.md「副作用随拥有者清理」；`references/composables.md`「DOM 交互与清理放在拥有它的 UI 或组合式函数里」
- 现状：
  ```ts
  const up = () => { window.removeEventListener("mousemove", move); /* …mouseup / touchmove / touchend */ };
  const move = (e: MouseEvent | TouchEvent) => handleHueDrag(e);
  window.addEventListener("mousemove", move);
  window.addEventListener("touchend", up);
  ```
  监听只在 `mouseup` / `touchend` 时移除，没有 `onBeforeUnmount` 兜底，也不处理 `touchcancel`。触摸拖动被系统手势打断时 `touchend` 不会来，这几个监听一直挂在 window 上：面板仍挂载时，之后在页面任意位置滑动手指都会改颜色，直到下一次 `touchend`；拖拽中浮层被关掉时监听也残留到下一次松手。`touchmove` 不阻止默认行为，触屏上拖滑块会同时滚动页面。三份几乎相同的实现让这类修复要改三遍。
- 改法：抽一个 `useDragHandle(elRef, onMove)`（放在组件同目录即可），内部用 Pointer Events + `setPointerCapture`，同时监听 `pointerup` / `pointercancel`，并在 `onBeforeUnmount` 里移除；滑块元素加 `touch-action: none`。`isDraggingSaturation`（`:140`、`:162`、`:165`）只写不读，可一并删掉。
- 影响：不改公开 API；UniApp 端用 touch 事件 + 选择器查询，实现不同，不需要同步；回归点是鼠标、触控笔、触屏三种拖动都要回测。

## reborn-context-menu

### [高] RebornContextMenu：根菜单 id 取自模块级计数器，SSR 时 `data-*` 属性水合不一致，导致点触发区被判成外部点击
- 位置：`app/components/reborn/ui/reborn-context-menu/context-menu-singleton.ts:10`、`app/components/reborn/ui/reborn-context-menu/context-menu-singleton.ts:27-30`、`app/components/reborn/ui/reborn-context-menu/RebornContextMenu.vue:212-219`、`app/components/reborn/ui/reborn-context-menu/RebornContextMenu.vue:569`、`app/components/reborn/ui/reborn-context-menu/RebornContextMenu.vue:788`、`app/components/reborn/ui/reborn-context-menu/RebornContextMenu.vue:796`
- 类别：SSR
- 依据：SKILL.md 将 SSR 列为默认关注点；`references/component-teleport.md` 关于 SSR 下浮层的处理；Vue 3.5 提供 `useId()` 专门生成服务端与客户端一致的 id
- 现状：
  ```ts
  let contextMenuRootCount = 0;
  export function createRootId(): string {
    contextMenuRootCount += 1;
    return `reborn-context-menu-${contextMenuRootCount}`;
  }
  ```
  ```vue
  <div :class="ui.wrapper()" :data-reborn-context-menu-root="rootController.rootId" …>
    <div ref="triggerRef" … :data-reborn-context-menu-root="rootController.rootId" @click="onClickTrigger">
  ```
  服务端进程里这个计数器跨请求一直累加，客户端每次从 1 开始，两边算出的 id 必然不同（只有进程启动后的第一次请求可能碰巧一致）。外层 `div` 与触发区在服务端渲染，水合时 Vue 不修正 `data-*` 属性，DOM 上永远留着服务端的 id；而 `onClickOutside` 用客户端的 id 做 `closest()` 判断（`:569`）。结果：`trigger="click"` 时菜单打开后再点触发区，`mousedown` 先被判为外部点击关掉菜单，紧接着的 `click` 又把它打开，用户无法通过触发区收起菜单；右键模式下在触发区内再次右键会跳过「先收起再换位展开」的过渡。开发环境还会刷水合告警。
- 改法：删掉 `createRootId`，在根实例里用 `useId()`：
  ```ts
  const rootController = injectedRoot ?? { rootId: useId(), closeAll: () => updateOpen(false) }
  ```

- 现状：布尔、数字、字符串类状态都用 `ref()` 声明。对原始值两者行为相同，`shallowRef` 少一层深层代理判断，也让「这里只会整体替换」的意图更明确。这是仓库范围的写法，单个组件收益很小。
- 改法：随各组件的其他改动顺手替换，不建议单独发起一轮全量修改。
- 影响：无。

### [低] DOM 模板引用写法不统一，未用 `useTemplateRef`
- 位置：`reborn-collapse/RebornCollapse.vue:47-48`；`reborn-color-picker/RebornColorPickerPanel.vue:139`、`:178`、`:206`；`reborn-context-menu/RebornContextMenu.vue:223-225`；`reborn-depth-image/RebornDepthImage.vue:93-95`；`reborn-descriptions/RebornDescriptions.vue:107`（均在 `app/components/reborn/ui/` 下）
- 类别：其他
- 依据：`references/sfc.md`「Vue 3.5+ 用 `useTemplateRef()` 访问 DOM / 组件引用」
- 现状：这些组件用 `ref<HTMLElement | null>(null)` 与同名变量隐式配对，同分片的 `RebornCrowd.vue:109-110` 已改用 `useTemplateRef`。隐式配对在变量改名时不会报错，只会静默拿到 `null`。
- 改法：统一为 `const rootRef = useTemplateRef<HTMLElement>('root')`，模板 `ref="root"`。
- 影响：无。
