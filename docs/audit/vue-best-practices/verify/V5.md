## 复核说明

- **SelectTrigger 的调用方**：7 个调用方（Select、Cascader、DatePicker、TimePicker、TreeSelect、Dropdown、BreadcrumbItem）逐个看过。`keydown` / `close` / `enter` / `afterEnter` 是声明过的 emit，调用方写的同名监听不会被当成透传属性。TimePicker 自己设了 `inheritAttrs: false`，把 `$attrs` 绑到内部输入框，不受影响。Cascader 已改为直接在 `<RebornSelectTrigger>` 上写 `@focusin` / `@focusout`（`RebornCascader.vue:724-725`）。BreadcrumbItem 的 `v-bind="props.dropdownProps"` 里的非 prop 键（例如为 UniApp 写的 `hideOnClick`）现在会落成 wrapper 上无害的 DOM 属性。各调用方的 `@close` 处理函数要么只读 `event?.target`（Dropdown、DatePicker），要么不读事件，所以 `mousedown` 换成 `pointerdown`、新增窗口失焦（iframe）关闭，都不会破坏它们。全仓库没有 `isOpening` 的外部消费方。
- **外部关闭时机**：`useFloatingDismiss` 的绑定由 `watch(open)` 在 pre 刷新时执行，触发展开的那次按下 / 点击已经过了 document 捕获阶段，不会被误判成外部点击；`closeOn: 'click'` 时 `closeOnScroll` 为 false，滚轮 / 触摸提前关闭也一并关掉，与 HEAD 语义一致。
- **Sticky**：从 824 行拆成主组件加 `useStickyMetrics` / `useStickyTop` / `useStickyBottom`。DOM 读取集中在 `measure()`，状态与样式只读快照。吸顶、吸底、overlay、target 停靠与 Collapse 动画协调，由 `tests/w4-w6/regressions.browser.test.ts:124-167` 在前台浏览器里覆盖，测试通过。逐分支与 HEAD 的旧实现对比后，新发现见下文「低」useStickyMetrics、动画登记键、文档三条。
- **其余组件**：Result、Segmented、Statistic 的改动与原改法一致，没有发现新问题；Steps 本轮无改动。

- 现状：
  ```ts
  const innerValue = shallowRef<RadioValue>(props.defaultValue)
  const currentValue = computed(() => (model.value !== undefined ? model.value : innerValue.value))
  function updateValue(value: RadioValue, _ev: Event) { innerValue.value = value; model.value = value; ... }
  ```
  Web 端（`app/components/reborn/ui/reborn-radio/RebornRadioGroup.vue:79`）和两端的 Switch 都已改好，但 UniApp RadioGroup 在受控模式下仍会写 `innerValue`，表单重置为 `undefined` 后继续显示上一次选中的项。整改自述把它列为「转交 U 分片」，当前源码还没落地；文档的两端通用表和注意事项却已经写成「绑定值被父级置回 undefined 时也回到该值」，UniApp 端与文档不符。

### [中] RebornSplitter：增删面板时相邻面板被补偿或扣减的尺寸不发 update:size，v-model:size 与实际尺寸失步
- 类型：新问题
- 原条目：无（由「高」挂载登记下标一条的快照方案引入）
- 位置：`app/components/reborn/ui/reborn-splitter/RebornSplitter.vue:160-198`（`resolveSizes` 只做纯推导，不通知）、`:248-265`（`applySizes` 是唯一调用 `sizeListeners` 的地方）；文档 `content/2.components/layout/reborn-splitter.md` Emits 表的 `update:size` 行
- 依据：`references/component-data-flow.md`「v-model 是双向契约」；`references/reactivity.md`「保持唯一数据源」
- 现状：
  ```ts
  // resolveSizes：被移除面板的份额补给相邻面板、新面板从相邻面板扣出，只算出结果，不写快照也不通知
  sizes[at] = (sizes[at] ?? 0) + (base.sizes[key] ?? 0)
  ...
  sizes[neighbor] = (sizes[neighbor] ?? 0) - take
  ```
  拖拽过（已有快照）之后用 `v-if` 插入或移除面板，相邻面板的实际宽度变了，它的 `v-model:size` 却还是旧值。`tests/reborn-splitter/splitter.browser.test.ts:198-227` 恰好覆盖这个场景：插入面板后 A 从约 55 变成约 45，测试只断言了宽度，没有断言 `state.first`，按源码推导它仍是 55。后果有两个：父级显示的尺寸与界面不符；父级想把它改回模型里那个旧值时，模型没有变化，面板的 `watch(size)` 不触发，改不回去。文档 Emits 表写的是「面板尺寸真正变化时触发」，与行为不符。
- 建议改法：二选一。（1）在 Splitter 渲染之后（`onUpdated`，或对渲染结果做 post 回调）比较 `rendered.sizes` 与上一次通知过的尺寸，对变化的面板调用 `sizeListeners`；不要在渲染函数里直接 emit。（2）增删面板时把 `resolveSizes` 的结果写回快照，走 `applySizes` 的通知路径。无论选哪种，文档 Emits 表与「注意事项」都要写清增删面板会不会触发 `update:size`。

### [低] RebornSplitter：默认插槽里的任何组件节点都被当作面板；被元素包裹的 SplitterPanel 会直接抛错
- 类型：新问题
- 原条目：无（由「高」挂载登记下标一条的渲染期 Scope 方案引入）
- 位置：`app/components/reborn/ui/reborn-splitter/RebornSplitter.vue:104-106`（`isPanel: !!(node.shapeFlag & 6)`）、`:116-125`（从该节点的 vnode props 读配置）；`app/components/reborn/ui/reborn-splitter/RebornSplitterPanel.vue:48-52`（缺少位置上下文就 `throw`）
- 依据：`references/component-data-flow.md`「Report a missing required provider clearly」「consumer helpers inject that instance」
- 现状：识别面板只看「是不是组件 vnode」，不看是不是 `RebornSplitterPanel`。
  - 默认插槽里放了非面板组件（如 `<ClientOnly>`、业务包装组件）时，它会被包进 Scope、分到一份尺寸并计入 `count`；配置从这个包装组件的 vnode props 读取，包装组件没有用同名 prop 转发 `size` / `min` / `max` 时全部失效。
  - 面板外面包了一层原生元素（`<div><RebornSplitterPanel/></div>`）时，元素节点不进 Scope，面板注入不到 `splitterPanelPositionKey`，`RebornSplitterPanel.vue:51` 直接抛错，整棵树渲染失败。HEAD 的挂载登记写法下，这两种用法至少不会抛错（包装组件里的面板能登记到自己的配置）。
  - 仓库内的 demo 和文档都是面板直挂，暂时没踩到。
- 建议改法：`collectNodes` 只把 `node.type === RebornSplitterPanel`（或面板上的一个静态标记）视为面板，其余组件原样渲染；在文档「注意事项」写明「面板必须是 Splitter 的直接子节点（可以经过 `v-for` / `v-if` / `<template>`）」；`throw` 改成开发环境 `console.warn`，并降级为不参与尺寸分配，至少不要让整页崩溃。

### [低] RebornSelect：已选项缓存在选中或取消的那一刻就改写，父级拒收这次改动时可能丢掉原已选项的回显
- 类型：新问题
- 原条目：无（由「高」远程搜索丢失已选一条的缓存方案引入）
- 位置：`app/components/reborn/ui/reborn-select/RebornSelect.vue:756`（单选：`selectedCache.value = new Map([[option.value, option]])`）、`:736`（多选取消：先 `forgetSelected`）、`:611`（`removeTag` 后 `forgetSelected`）
- 依据：项目规则「受控绑定下赋值后同步读仍是旧值」；`references/reactivity.md`「派生值依赖的数据源要完整」
- 现状：单选时缓存先被整体替换成只含新选项，之后才执行 `model.value = option.value`。父级拒收（受控绑定不接收更新，或在 `update:modelValue` 里改回原值）时，绑定值仍是旧值 V0，缓存里却已经没有 V0；如果此时的 options 是远程搜索结果、不含 V0，触发器就回到占位符。多选的取消选中和 `remove-tag` 同理：先从缓存删掉，父级拒收后这个值还在，却因为不在当前 options 里而标签消失。触发条件是「远程搜索」叠加「父级拒收」，比较少见。
- 建议改法：选中时只追加、不清空（单选也用 `new Map(selectedCache.value).set(...)`），取消时不立即删除；清理放到 `watch(selectedSet)` 里，只删「既不在当前选中集合、也不在当前 options 里」的项，让缓存始终以已经生效的绑定值为准。

- 位置：`app/components/reborn/ui/reborn-select-trigger/RebornSelectTrigger.vue:102`、`:408`、`:475`、`:481`
- 依据：SKILL「Keep state predictable」；`references/reactivity.md`「保持最少的源状态」
- 现状：`isOpening` 只在 isOpen 的 watch、`onAfterEnter`、`onAfterLeave` 里被赋值，模板、计算属性、expose 都不再读它。它仍是一个 `shallowRef`，每次赋值都做一次无意义的依赖检查，也会让后来者误以为它驱动了某处行为。
- 建议改法：删除 `isOpening` 和三处赋值。

### [低] RebornSearchBox：`history` 用 `getCurrentInstance()` 读原始 vnode props 判断是否绑定，与 defineModel 形成两套受控判断
- 类型：新问题
- 原条目：无（由「中」历史记录契约一条引入）
- 位置：`app/components/reborn/ui/reborn-search-box/RebornSearchBox.vue:100-107`
- 依据：`references/component-data-flow.md`「Use defineModel for v-model」「Keep contracts explicit」；SKILL「one source of truth」
- 现状：
  ```ts
  const historyModel = defineModel<string[]>("history", { default: () => [] });
  const instance = getCurrentInstance();
  const historyBound = () => "history" in (instance?.vnode.props ?? {});
  const history = computed(() => historyBound() ? (instance?.props.history as string[] ?? []) : historyModel.value);
  ```
  `defineModel` 本身已经区分「父级绑定」和「本地持有」，这里又用内部实例 API 再判断一遍，于是同一份历史有两个读取口：`writeHistory` 写 `historyModel`，展示读 `instance.props.history`。只传 `:history` 不监听更新时，`historyModel` 在本地更新，界面却读父值，两者分叉。`vnode.props` 也不是响应式来源，`historyBound()` 放在 computed 里能工作，只是因为同时读了响应式的 `instance.props.history`。目前功能没出错，但正确性依赖这些隐含前提。
- 建议改法：展示与写入都只走 `historyModel.value`。是否写本地存储改用一个显式信号判断，例如 `defineModel` 不给默认值、未绑定时以 `historyModel.value === undefined` 为准，本地兜底另存一个 `shallowRef`；不再读 `getCurrentInstance()`。

### [低] useStickyMetrics：每次测量都整体替换快照，数值没变也会让下游 watch 与 `contentStyle` 重算、组件重渲染
- 类型：新问题
- 原条目：无（由「中」computed 读 DOM 与「低」职责集中两条的拆分引入）
- 位置：`app/components/reborn/ui/reborn-sticky/useStickyMetrics.ts:24-36`（`measure` 每次 `metrics.value = { ... }`）、`:59`（`window` 捕获阶段的 scroll）；下游 `RebornSticky.vue:74-81`、`:116-134`，`useStickyTop.ts:8`，`useStickyBottom.ts:16`
- 依据：`references/reactivity.md`「Avoid unnecessary re-renders」「shallowRef 只在整体替换时触发」；`references/updated-hook-performance.md`「高频更新路径要尽量轻」
- 现状：scroll 监听挂在 `window` 的捕获阶段，页面上任何容器滚动（包括与 Sticky 无关的内部列表）都会排一次 rAF 测量。`measure()` 每次都写入新对象，`shallowRef` 按引用判断变化，于是三个 watch 全部重跑，`contentStyle` 返回新对象，组件每帧重渲染并重写行内样式。HEAD 用的是 `useElementBounding` 的数值 ref，值不变时不触发下游。页面上有多个 Sticky、同时滚动内部容器时，每帧就是 N 次无效渲染。
- 建议改法：`measure()` 先组装新快照，逐字段与当前值比较，全部相同就不赋值；或者把 `contentStyle` 依赖的几个数值拆成独立的 `shallowRef`，只在变化时写入。

### [低] RebornSticky：动画登记键定义在 Collapse 的样式配置文件里，Sticky 因此依赖整个 Collapse 组件
- 类型：新问题
- 原条目：无（由「低」Sticky 与 Collapse 靠类名耦合一条引入）

- 依据：SKILL「Choose useful boundaries」「Make data flow explicit」；`references/component-data-flow.md`「Use typed, scoped provide/inject」
- 现状：用类型化的 provide / inject 取代类名嗅探，方向是对的（Sticky 提供、Collapse 登记）。问题是这个通用的「布局动画中」契约放在 Collapse 的 tailwind-variants 配置文件里。Sticky 为了一个 Symbol 依赖 Collapse 的样式文件；CLI 按 `../<组件名>/` 解析组件依赖（`packages/cli/src/utils/dependencies.ts:17`），安装 Sticky 会连带装上整个 Collapse；以后其他有展开动画的组件要接入，也得反向依赖 Collapse。
