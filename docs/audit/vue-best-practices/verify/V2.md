## 需要处理的问题

按严重度排序。问题 1~8 对应判定为「修复有误」的原条目（含同一原条目的文档残留），新问题 1~6 为不属于任何原条目的整改副产物。

### 问题 1 [中] RebornCascader / RebornCascaderPanel：fieldNames、loadMore 一换引用就清空懒加载缓存，内联写法下父级任意一次重渲染都会让已加载的下级消失
- 类型：修复有误
- 原条目：W2-04 [中] RebornCascaderPanel：懒加载把子节点直接写回 props.options，改的是父级数据，而且依赖它是深层响应式
- 位置：`app/components/reborn/ui/reborn-cascader/reborn-cascader.context.ts:25-29`
- 依据：`references/reactivity.md`「watchers 只做副作用，触发源要对应真正的输入变化」；`references/component-data-flow.md`「父级传入的函数 / 对象引用不是稳定契约」
- 现状：
  ```ts
  watch(() => [props.options, props.fieldNames, props.valueKey, props.loadMore], () => {
    generation++;
    loadedChildren.value = new Map();
  ```
  getter 每次重跑都返回新数组，四个 prop 任一换了引用就清空缓存。模板里写 `:load-more="(o, done) => fetchChildren(o, done)"`，或 `:field-names="{ label: labelKey }"`（引用了绑定，编译器不会当常量），父级每次重渲染都会生成新的函数 / 对象。最常见的触发就是选中懒加载出来的子项：v-model 回写让父级重渲染，缓存被清空，刚加载出的那一列消失，标签回显也找不到节点。整改前子节点写进 options 对象本身，不受这两个 prop 换引用影响，所以这是回归。已用临时脚本复现：options 引用固定，只把 `loadMore` 写成内联箭头函数，加载完成后让父级重渲染一次，子项从 DOM 中消失（输出 `before true after false`）。文档 `reborn-cascader.md:563` 只写了「替换 loadMore 会清空缓存」，使用者意识不到内联写法等于每次都在替换。
- 建议改法：缓存只跟数据走。`loadMore` 不参与清空（在途请求只在 options 变化时作废即可）；`fieldNames` 按取值比较，例如 watch `() => JSON.stringify(props.fieldNames ?? {})`；`options`、`valueKey` 用多源数组 `watch([() => props.options, () => props.valueKey], …)` 逐项比较。同时把文档第 563 行改为「替换 options 数组、改变 valueKey 或 fieldNames 的取值会清空缓存」。

### 问题 2 [中] RebornBreadcrumb：按组件身份识别条目，全局注册 / 运行时解析拿到的是异步包装组件，max-count 折叠与 order 排序完全失效
- 类型：修复有误
- 原条目：W2-05 [中] RebornBreadcrumb：插槽模式下条目按 setup 先后登记，中途插入的条目会排到末尾，折叠时隐藏错项、视觉顺序错乱；SSR 首屏不折叠
