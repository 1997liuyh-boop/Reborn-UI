## 需要处理的问题

### [高] RebornToast：「只让最后挂载的页面实例渲染」在 tabBar 页面之间失效，切回先打开的标签页后消息全部渲染到隐藏页里
- 类型：修复有误
- 原条目：[低] reborn-toast/index.ts：H5 命令式容器在事件回调里拿不到实例，appContext 桥接实际不生效；容器挂上后还会和页面内实例重复渲染（待确认）
- 位置：`packages/uniapp-project/src/components/reborn-toast/reborn-toast.config.ts:133-147`；`packages/uniapp-project/src/components/reborn-toast/RebornToast.vue:28-31`、`:73`
- 依据：component-data-flow.md「Provide/Inject：match its lifetime to the intended scope」——渲染者的归属要和「当前可见页面」的生命周期一致；SKILL.md 自检「Refactors preserve existing behavior」
- 现状：
  ```ts
  function selectRenderer() {
    const entries = [...renderers]
    messageRenderer.value = [...entries].reverse().find(([, container]) => !container)?.[0] ?? entries.at(-1)?.[0]
  }
  // RebornToast.vue
  const isRenderer = computed(() => messageRenderer.value === instance.uid)
  <view v-if="isRenderer" ...>
  ```
  渲染者只在实例挂载 / 卸载时重选，取「最后挂载的页面实例」。每个页面都通过 `RebornPage` 内置一个 `RebornToast`（`reborn-page/RebornPage.vue:54`）。uni-app 的 tabBar 页面（小程序原生 tabBar 与 H5 的 keep-alive 标签页）切换时不卸载：先进入标签页 A（实例 1），再切到标签页 B（实例 2，成为渲染者），切回 A 后没有任何挂载 / 卸载，渲染者仍是 B。此后在 A 上调用 `Message.success(...)`，消息只渲染在隐藏的 B 页里，A 页上什么都看不到。改动前每个页面实例都渲染共享的 `messageState.list`，不存在这个问题。原报告只要求处理 H5「命令式容器与页面实例重复渲染」，整改把仲裁扩大到了所有页面实例和小程序端（本仓库演示工程没有配置 tabBar，所以现有演示与测试覆盖不到）。
- 建议改法：仲裁只在「命令式容器」和「页面实例」之间做，页面实例之间保持各自渲染（隐藏页本来就不可见）：
  ```ts
  /** 页面实例全部照常渲染；命令式容器只在没有任何页面实例时渲染 */
  const isRenderer = computed(() => !isContainer || pageInstanceCount.value === 0)
  ```
  `pageInstanceCount` 用一个 `shallowRef` 计数（页面实例挂载 +1、卸载 -1）。如果确实要在页面之间去重，需按「当前显示的页面」选择（由 `RebornPage` 的 `onShow` 上报），不能按挂载先后。修好后在 H5 与微信开发者工具里各验证一次：配置两个 tabBar 页面，来回切换后分别弹消息。

  ```ts
  const key = Object.hasOwn(raw, name) ? name : hyphenated   // useRawProp.ts:53
  ... ?? entries.at(-1)?.[0]                                  // reborn-toast.config.ts:135
  ```
  iOS 上的微信小程序跑在系统 JavaScriptCore 里，`Object.hasOwn` 与 `Array.prototype.at` 都是 Safari 15.4 才有；H5 在旧版 iOS WebView 里同理。在这些环境上，`useRawProp()` 第一次执行就抛 `TypeError`，所有用到 `useFormInject` 的控件和用到 `useBooleanModel` 的组件 setup 失败，整页渲染不出来。
- 建议改法：换成不依赖新内置方法的写法：`Object.prototype.hasOwnProperty.call(raw, name)`、`entries[entries.length - 1]`（`app/utils/themeColor.ts:16` 的启动脚本已经是这种写法，可作参照）。需要在 iOS 15.4 以下真机（或关闭「增强编译」的开发者工具）上确认一次；如果项目明确只支持 iOS 15.4+，在 UniApp 包的文档里写明最低系统版本，并把这一条降为低。

### [低] RebornSticky：吸顶状态切换后的内部重测也改写了 top，用的是回调时刻的节流 scrollTop，临界点附近可能来回切换（需实测）
- 类型：新问题
- 原条目：无（由 [中] RebornSticky getRect 一条的改法引出）
- 位置：`packages/uniapp-project/src/components/reborn-sticky/RebornSticky.vue:126`、`:147-149`
- 依据：reactivity.md「Keep source state minimal」：同一个派生值（吸顶触发点）的两个输入要取自同一时刻；原报告建议内部重测传 `{ position: false }`，或在同一个 query 里用 `selectViewport().scrollOffset()` 取滚动量，整改两者都没采用
- 现状：
  ```ts
  rect.top = (node.top ?? 0) + scrollTop.value   // :126，scrollTop 是父级 onPageScroll 传进来的 prop
  watch(isSticky, () => { nextTick(() => { if (!disposed) getRect() }) })  // :147
  ```
  `node.top` 是渲染层执行查询那一刻的位置，`scrollTop.value` 是回调回到逻辑层时的 prop，滚动中两者相差一次跨线程往返的滚动量。原实现只在首次测量时记 top，规避了这一点；现在每次吸顶切换都会用错位的两个值重算触发点，触发点随滚动方向偏前或偏后，在临界位置可能出现吸顶 / 取消吸顶来回跳。误差有界、不会累积，但会造成闪动。
