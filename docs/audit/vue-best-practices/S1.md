### [高] AppThemePicker：主题色只在 ClientOnly 里的组件中写入 `<html>`，首屏不生效；首页、/playground、/preview 根本不应用用户选的主题色
- 位置：
  - `app/components/app/AppThemePicker.vue:37-42`（读 cookie、`useHead` 写 `data-theme-color`）
  - `app/components/app/AppHeader.vue:204-214`（`<ClientOnly>` 包着 `<AppThemePicker />`）
  - `app/app.vue:96`（`<AppHeader v-if="$route.meta.header !== false" />`）
  - `app/pages/index.vue:20`、`app/pages/playground.vue:15`、`app/pages/preview/[component].vue:40`（`header: false`）
- 类别：SSR / 组件边界
- 依据：`vue-debug-guides/reference/ssr-hydration-mismatch-causes.md`、`lifecycle-ssr-awareness.md`：服务端没执行到的副作用，首屏就拿不到；`references/composables.md`「状态的生命周期要和它的作用范围一致」。
- 现状：
  ```ts
  // AppThemePicker.vue:37-42
  const themeColor = useCookie<string>('theme-color', { default: () => 'blue' })
  // SSR 阶段就把属性写进 <html>，避免首屏先按默认色渲染、水合后再跳一次色
  useHead(computed(() => ({ htmlAttrs: { 'data-theme-color': current.value.preset } })))
  ```
  注释的前提不成立，原因有三：
  1. **服务端根本不执行**：组件挂在 `AppHeader.vue:204` 的 `<ClientOnly>` 里，服务端只输出占位，`useHead` 不会运行。客户端要等水合完成、ClientOnly 挂载后才写属性。选了橙 / 绿 / 红的用户，每次整页加载都会先看到品牌蓝，再跳色。
  2. **预渲染页面读不到 cookie**：Docus 开了 `nitro.prerender.crawlLinks`，文档页是构建期生成的静态 HTML，构建时没有用户 cookie。所以就算挪出 ClientOnly，「SSR 读 cookie」这条路对预渲染页面也无效。
  3. **属性跟着顶栏的生命周期走**：`useHead` 条目属于 AppThemePicker 实例。首页、`/playground`、`/preview/*` 设了 `header: false`，AppHeader 不渲染：
     - 直接打开这些页面时，属性从没写过；
     - 从文档页跳过去时，AppHeader 卸载，`useHead` 条目被移除，`data-theme-color` 随之消失；
     - 文档页 DemoStage 的设备档 iframe 加载的是 `/preview/<demo>?embed=1`，iframe 里的示例也一律是默认主题色，和外面的页面不一致。
- 改法：
  - 主题色状态从选择器组件里拿出来，放到全站常驻的位置。例如新建 `app/plugins/theme-color.ts`（或写在 `app.vue` 里），在那里读 cookie 并 `useHead({ htmlAttrs: { 'data-theme-color': ... } })`。AppThemePicker 只负责改 cookie。
  - 首屏不跳色：在 `useHead` 里注入一段很小的阻塞脚本（`tagPosition: 'head'`），在首次绘制前读 `document.cookie` 写 `document.documentElement.dataset.themeColor`。做法和 color-mode 模块处理暗色的方式相同，这样对预渲染页面也有效。
  - DemoStage 的 `syncTheme`（`app/components/common/demo-stage/DemoStage.vue:57-61`）在同步 `dark` 类时，顺带同步 `data-theme-color`。如果 `/preview` 页已经由上面的插件处理，这一步可以省掉。
- 影响：
  - 不改公开 API。
  - 回归点：切色后刷新、在首页 / Playground / 预览页之间来回跳、暗色模式下切色。
  - 可以和 `useDocsPlatform` 的「水合后从 localStorage 恢复」放在同一类插件里统一管理。

### [高] ComponentsList：总览页把全部组件文档的完整正文 AST 塞进 payload，构建产物 `components/_payload.json` 有 6.28 MB
- 位置：
  - `app/components/common/component-list/ComponentsList.vue:23-26`（`queryCollection('docs').all()` 后在内存里过滤）
  - `app/components/common/component-list/ComponentsList.vue:74-86`、`142`（只为了从 `body` 里找 `demo-file` 才保留正文）
- 类别：SSR / 性能
- 依据：
  - `references/reactivity.md`「大数据只保留需要的部分」；
  - Nuxt 的 `useAsyncData` 会把返回值整份序列化进 payload，客户端水合时要下载并解析这份数据。
- 现状：
  ```ts
  const { data: components } = await useAsyncData('tools', async () => {
    const docs = await queryCollection('docs').all() as DocsCollectionItem[]
    return docs.filter(item => item.path.startsWith(routePath) && item.path !== routePath)
  })
  ```
  返回值是 173 篇组件文档的完整记录，每篇都带 `body`（整篇 minimark AST）、`toc`、`seo` 等字段。卡片实际只用到 id、path、title、description、category、series、platform、badge、tags，外加从 `body` 里推出来的一个 demo 名。
  - 现有产物 `.output/public/components/_payload.json` 有 6,280,399 字节。其中键 `tools` 指向的数据从第 912 项一直占到第 288,047 项，几乎是整份 payload。
  - 页面 HTML 里的 `<script id="__NUXT_DATA__" data-src="/components/_payload.json?…">` 说明水合依赖这份文件：
    - 首次打开 `/components` 时，要先下完、解析完这 6 MB，再还原成响应式对象，页面才可交互；
    - 从别的页面站内跳转过来时，同样要先拉这份 payload。
  - 另外，`'tools'` 这个 key 是写死的，没有包含 `routePath`。将来如果用不同的 `routePath` 再渲染一份总览，两份会命中同一条缓存。
- 改法：在取数函数里就把数据裁成卡片需要的形状，payload 里只放这一小份。
  ```ts
  const { data: components } = await useAsyncData(`components-overview:${routePath}`, async () => {
    const docs = await queryCollection('docs').all() as DocsCollectionItem[]
    return docs
      .filter(item => item.path.startsWith(routePath) && item.path !== routePath)
      .map(item => ({
        id: item.id, path: item.path, title: item.title, description: item.description,
        category: item.category, series: item.series, platform: item.platform,
        badge: item.badge, tags: item.tags,
        demoName: overviewNameFromItem(item), // 在这里就把 body 用完丢掉
      }))
  })
  ```
  更进一步：给 `docs` 集合加一个 `overviewDemo` 之类的派生字段，或者用 `.select(...)` 只取需要的列，连服务端查询都不读正文。
- 影响：
  - 不改公开 API。
  - `overviewItems`（`ComponentsList.vue:127-149`）改为读裁剪后的字段。
  - 回归点：卡片标题 / 英文名 / 平台徽标 / 缩略图名称推导、平台切换后的筛选。
  - 改完后对比 `_payload.json` 体积，预期降到几十 KB。

### [高] layouts/docs.vue：用 `route.fullPath` 判断「是否根页」，带 query 或 hash 访问 /components、/changelogs 时服务端与客户端渲染出两套布局
- 位置：
  - `app/layouts/docs.vue:3`、`12`、`76-77`（`isRoot` 决定 body 类名、UPage 的 `ui` / `style`、是否渲染 `#left` 侧栏）
  - `app/utils/isRootPage.ts:4-10`（比较 `route.fullPath`，属于 C1 分片）
  - `app/components/common/component-list/ComponentsList.vue:288`（总览头图里的 `href="#series-…"` 锚点）
- 类别：SSR / 响应性
- 依据：`vue-debug-guides/reference/ssr-hydration-mismatch-causes.md`：服务端拿不到的输入（这里是 URL 的 hash，以及预渲染时不存在的 query）参与了首帧渲染分支。
- 现状：
  ```ts
  // isRootPage.ts
  return computed(() => rootPages.findIndex(item => item === route.fullPath) >= 0)
  ```
  `fullPath` 包含 query 和 hash：
  1. **直接打开带后缀的地址**，例如分享出去的 `/components#series-community`，或者带统计参数的 `/components?utm_source=x`：
     - 预渲染 HTML 是按 `/components` 生成的，`isRoot = true`，没有左侧栏，用的是根页栅格；
     - 客户端路由的 `fullPath` 带着后缀，`isRoot = false`，模板多出 `#left` 侧栏，并换成三栏的 `ui`。
     - 结果是水合不一致：元素增减会被重建；但 class 不一致在生产环境只告警、不修正，所以栅格类停留在服务端版本，侧栏却被插进来，版式错乱。同时 body 上被挂上 `layout-admin-shell`。
  2. **站内点总览头图的系列锚点**（`ComponentsList.vue:288`，lg 以上可见）：片段导航会更新路由的 hash，`isRoot` 随之变成 false，总览页上凭空出现左侧菜单，容器宽度也被放开。这条依赖浏览器在片段导航时触发 `popstate`、Vue Router 随之更新路由，**待确认**：在浏览器里点一次锚点即可验证。
- 改法：只比较路径，并统一去掉尾斜杠。
  ```ts
  const normalized = computed(() => route.path.replace(/\/$/, '') || '/')
  return computed(() => rootPages.includes(normalized.value))
  ```
- 影响：
  - 不改公开 API。
  - `isRootPage.ts` 属于 C1 分片，改的时候要同步那份报告。
  - 回归点：`/components`、`/changelogs` 加 query / hash 直接打开；总览页点系列锚点；普通文档页的三栏布局不受影响。

### [中] DocsMobilePanel：iframe 重新挂载时用的是第一次的 `initialUrl`，跨页切换后再切平台或缩放窗口，会显示上一个页面的 demo
- 位置：
  - `app/components/docs/DocsMobilePanel.vue:98-100`（`initialUrl` / `shownUrl`）
  - `app/components/docs/DocsMobilePanel.vue:106-141`（两个 watch）
  - `app/components/docs/DocsMobilePanel.vue:242-243`（`v-if="shouldMountFrame && h5Available && initialUrl"`、`:src="initialUrl"`）
  - `app/layouts/docs.vue:54-55`（与实现不符的注释）
- 类别：数据流 / 生命周期与清理
- 依据：`references/reactivity.md`「保持唯一数据源，其余派生」：iframe 实际该加载的地址应当从 `activeUrl` 派生，而不是另存一份只在特定分支更新的快照。
- 现状：
  1. 在页面 A（UniApp 档、宽度 ≥ 1536px）上，iframe 以 `initialUrl = A` 挂载。
  2. 切到页面 B 时，`watch(activeUrl)` 走的是「同源 hash 导航」分支：`location.replace(B)`，`shownUrl = B`，但 **`initialUrl` 仍然是 A**。
  3. 这时把顶栏切到 Web，或把窗口缩到 2xl 以下：`shouldMountFrame` 变成 false，iframe 被 `v-if` 卸载。
  4. 切回 UniApp 或放大窗口：iframe 重新挂载，`:src="initialUrl"` 加载的是页面 A 的 demo。正文已经是 B，右栏仍显示 A，要手动点「刷新预览」才会纠正。
  - 另外：`watch(activeUrl)` 没有 `immediate`。现在能正常工作，是因为 demo 注册发生在面板挂载之后——`ComponentPlayground` 只用在 `components/reborn/configs/**` 里，而 `nuxt.config.ts` 把这些组件设成了 `mode: "client"`。
    - `docs.vue:54-55` 的注释写的是「demo 注册在 SSR 期即由 ComponentPlayground 完成（useState 随 payload 下发）」，与实际不符。
    - 如果以后有人照着注释把注册改到 SSR 期，`activeUrl` 在面板 setup 时就已经有值，watch 不会触发，`initialUrl` 永远为 null，iframe 永远不挂载。
- 改法：
  - iframe 每次（重新）挂载时，都以当前 `activeUrl` 为准：
    ```ts
    watch(shouldMountFrame, (mount) => {
      if (!import.meta.client || !mount) return
      isLoading.value = true
      initialUrl.value = activeUrl.value
      shownUrl.value = activeUrl.value
      if (h5Available.value === null) probeH5()
    }, { immediate: true })
    ```
  - `watch(activeUrl)` 加上 `immediate: true`，首个分支对「已有值」同样成立。
  - 修正 `docs.vue:54-55` 的注释：注册在客户端挂载后完成，平台档位水合后才恢复，所以首帧一定不显示面板。
- 影响：
  - 不改公开 API。
  - 回归点：同一会话里在多个带 uniapp demo 的页面之间跳转、Web / UniApp 来回切、跨 2xl 断点缩放、手动刷新、H5 产物缺失时的兜底提示。

### [中] ComponentOverviewDemo：每张还没进入视口的卡片都在 window 上挂一个捕获阶段的 scroll 监听，每次滚动逐个读取 `getBoundingClientRect`
- 位置：`app/components/common/component-list/ComponentOverviewDemo.vue:77-105`
- 类别：性能 / 生命周期与清理
- 依据：
  - `references/composables.md`「Keep DOM interaction and cleanup with its owning UI」：同一件事应当只有一个共享实现；
  - `vue-debug-guides/reference/lifecycle-hooks-synchronous-registration.md`：生命周期钩子要在 setup 中同步注册。
- 现状：
  ```ts
  const io = new IntersectionObserver(…)
  io.observe(el)
  // 部分预览环境 IO 不回调：滚动时用几何再判一次
  const onScrollCheck = () => { … if (isNearViewport(el)) { … } }
  window.addEventListener('scroll', onScrollCheck, true)
  onBeforeUnmount(() => { io.disconnect(); window.removeEventListener('scroll', onScrollCheck, true) })
  ```
  - 总览页有 150 多张卡片，首屏以外的都会走到这里。于是：
    - 每张卡片各建一个 IntersectionObserver；
    - 另外在 window 上各挂一个**捕获阶段**的 scroll 监听。捕获阶段意味着页面上任何元素的滚动都会触发它们。
