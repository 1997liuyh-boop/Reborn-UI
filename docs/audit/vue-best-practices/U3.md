# U3：UniApp 组件库（reborn-slide-verify ~ reborn-watermark）

- 分片范围：`packages/uniapp-project/src/components/` 下 `reborn-slide-verify`、`reborn-slider`、`reborn-sticky`、`reborn-swiper-action`、`reborn-switch`、`reborn-tabbar`、`reborn-tabs`、`reborn-text`、`reborn-textarea`、`reborn-toast`、`reborn-transition`、`reborn-waterfall`、`reborn-watermark` 共 13 个目录。`components/` 根目录下没有不属于子目录的 `.vue` / `.ts` 文件。
- 文件数：40（`.vue` 15、`.ts` 25），逐个读完，清单见文末「覆盖清单」。
- 问题数：高 3 / 中 10 / 低 15。
- 审查前提：
  - 目标端含微信小程序与 H5。小程序端（uni-mp-vue）不支持渲染函数、Teleport、Transition，也拿不到 DOM API；下面的改法默认两端都能用，只适用于 H5 的会单独注明。`// #ifdef` / `// #endif` 条件编译一律保留。
  - UniApp 端没有 SSR，SSR / 水合类问题不适用。
  - 全部结论来自静态阅读，没有运行。需要真机或开发者工具确认的地方标了「待确认」。

## 有意未列为问题的写法

- `ui` 计算属性返回一组槽函数、模板里逐个调用：这是全仓库统一的模式，不单独上报，只在拖拽、列表这类热路径里单列（见「模板里逐项现算样式」一条）。
- RebornSlider 用 `fieldGroupDisabled.value === true || props.disabled === true` 判断整体禁用：符合项目规则（`useFormInject` 的 disabled 可能是数组）。
- RebornTransition 写两个根分支（`v-if` / `v-else-if`），只是为了切换 `@touchmove.stop.prevent`：小程序端不能按条件绑定事件修饰符，这是规避写法。
- RebornToast 用 keyframes、RebornTabPane 用切换类名代替 `Transition` / `TransitionGroup`：小程序端没有这两个内置组件，是刻意的。
- RebornSwiperAction 用模块级 `activeSwiperActions` 表做同组互斥：UniApp 没有 SSR，模块单例可以接受，卸载时也已清理（`:1577`）。
- style 对象里带前导连字符的 kebab-case 键（RebornTabbar `'z-index'`、RebornText `'-webkit-line-clamp'`、RebornTabs `'transition-duration'`）：小程序端反而必须这样写，原因见「Webkit 前缀用 camelCase」一条。
- RebornTabbar / RebornTabbarTrigger 依赖的 `useChildren` / `useParent` 属于 C1 分片，那里的问题不在这里记。

### [高] RebornSwitch：表单级禁用只作用到按压反馈，点击照样切换取值
- 位置：`packages/uniapp-project/src/components/reborn-switch/RebornSwitch.vue:75`、`:146`、`:159`、`:197`、`:203`；`reborn-switch.config.ts:32-107`（没有 disabled 变体）
- 类别：数据流
- 依据：SKILL.md 核心原则「Keep state predictable: one source of truth」；Web 端同名组件已修过同一个问题：`app/components/reborn/ui/reborn-switch/RebornSwitch.vue:226-227` 的注释写明「isDisabled 含表单级禁用，仅判 props.disabled 会漏掉 Form 下发的禁用态」
- 现状：
  ```ts
  const isDisabled = computed(() => formDisabled.value || props.disabled || props.loading) // :75
  async function onTap() {
    if (props.disabled || props.loading) return // :159
  ```
  `isDisabled` 已经合并了表单禁用，但只用在 `hover-class` 和 `data-disabled` 上；`onTap` 和 `updateValue`（`:146`）都只看 `props.disabled`。所以在 `<RebornForm disabled>`（例如查看态表单）里，开关的按压反馈没了，点击却照样切换，并 emit `update:modelValue` / `change`、触发 change 校验。`ui` 计算（`:86-94`）也没有把禁用态传给 tv，表单禁用时外观和可用态一样（样式本身不在本次范围，这里只作为「用户察觉不到已禁用」的旁证）。
- 改法：两处判断都改成读同一个来源：
  ```ts
  async function onTap() {
    if (isDisabled.value) return
    // ……原有逻辑
  }
  function updateValue(checked: boolean) {
    // beforeChange 异步期间表单可能被改成禁用，这里的二次判断要保留
    if (isDisabled.value) return
    // ……原有逻辑
  }
  ```
  本组件的 `disabled` 是纯布尔，沿用 `||` 不会出现数组误判。视觉禁用态可以参照 Web 端，在 tv 入参里补 `disabled`，另行处理。
- 影响：不改公开 API，行为与 Web 端对齐。回归点：`loading` 时仍不可点（`isDisabled` 已包含 loading）；表单整体禁用的 demo 需要复测。

### [高] RebornWaterfall：append 延时 300ms 测量，既不排队也不作废，连续追加或刷新后追加会丢数据、塞进 undefined，并在渲染时抛错
- 位置：`packages/uniapp-project/src/components/reborn-waterfall/RebornWaterfall.vue:101-142`（append）、`:106`、`:119`（setTimeout 300）、`:122`（`selectAll('.is-virtual')`）、`:126-138`、`:173-180`（clear 不取消待执行的测量）、`:212`（模板读 `item[props.nodeKey]`）
- 类别：生命周期与清理
- 依据：reactivity.md「Clean up async effects for watchers」：快速连续触发时，旧的异步结果必须作废；composables.md「Keep related state, actions, and lifecycle cleanup together」
- 现状：
  ```ts
  columns.value[0].push(...data.map(e => ({ ...e, isVirtual: true })))  // :106
  setTimeout(() => { /* selectAll('.is-virtual') */ .exec((rect) => {
    (rect[0] as any[]).forEach((e, i) => {
      columns.value[index].push(data[i])                                    // :132
      columns.value[0] = columns.value[0].filter(e => e.isVirtual != true) // :138
  ```
  定时回调查的是「此刻页面上所有虚拟项」，取数据时却用的是本批的 `data[i]`：
  1. 300ms 内又调了一次 `append(b2)`：第一批的回调量到的是 b1 和 b2 的全部虚拟项，下标超出 b1 长度的位置都 push 了 `undefined`，模板 `:212` 读 `item[props.nodeKey]` 直接抛 TypeError；`:138` 还会顺手删掉 b2 的虚拟项，等第二批回调执行时已经查不到 `.is-virtual`，b2 整批丢失。
  2. 下拉刷新：`clear()` 之后马上 `append(新数据)`，上一批的定时器照常执行，把旧数据塞回刚清空的列，新数据反而被当成虚拟项删掉。

  测量期间虚拟项是 `absolute opacity-0`，首屏实际没有内容高度，`onReachBottom` 很可能在第一批回调之前就触发了第二次加载，所以这是真实会碰到的竞态。另外组件在这 300ms 内卸载时，`rect[0]` 可能为 null，`.forEach` 也会抛错。
- 改法：每批虚拟项带上批次号，串行处理，`clear()` 和卸载时作废在途批次：
  ```ts
  let generation = 0                 // clear() 与卸载时自增，作废在途批次
  let batchSeed = 0
  let queue: Promise<void> = Promise.resolve()

  function append(data: any[]) {
    const gen = generation
    queue = queue.then(() => appendBatch(data, gen))
    return queue
  }

  async function appendBatch(data: any[], gen: number) {
    if (gen !== generation) return
    await getHeight()
    const batch = `b${++batchSeed}`
    // 模板上给虚拟项加 `is-virtual-${item.__batch}` 类名，只量本批
    columns.value[0].push(...data.map(e => ({ ...e, isVirtual: true, __batch: batch })))
    await nextTick()
    await new Promise(r => setTimeout(r, 300))
    if (gen !== generation) return
    const rects = await queryRects(`.is-virtual-${batch}`)
    if (!rects || gen !== generation) return
    columns.value[0] = columns.value[0].filter(e => e.__batch !== batch) // 循环外过滤一次
    rects.forEach((e, i) => { /* 找最短列，push(data[i])，累加高度 */ })
  }

  function clear() { generation++; /* ……原有重建列 */ }
  onBeforeUnmount(() => { generation++ })
  ```
- 影响：暴露方法的签名不变；`append` 返回的 Promise 改为在真正分列之后才 resolve（原来在测量之前），属于行为修正，文档若写了 append 的时序要同步。Web 端没有同名组件。

- 位置：`packages/uniapp-project/src/components/reborn-watermark/RebornWatermark.vue:81`、`:91-96`、`:115-122`
- 类别：组件边界
- 依据：composables.md「Keep DOM refs, focus, and pointer handling with their owning UI」：查询组件内节点要限定在组件自己的作用域。uni-app 规定在自定义组件里调用 `uni.createCanvasContext(canvasId, componentInstance)` 和 `uni.canvasToTempFilePath(object, componentInstance)` 必须传第二个参数，否则只在页面作用域里找。同仓库的 `reborn-qrcode/RebornQrcode.vue:130`、`:177` 和 `reborn-signature/RebornSignature.vue:466`、`:509` 都传了 `proxy`。

  ```ts
  const ctx = uni.createCanvasContext(canvasId)        // :81 没传实例
  uni.canvasToTempFilePath({ canvasId, success })       // :91、:115 没传实例，也没有 fail 分支

  H5 端按 canvas-id 全局查找，能画出来。微信小程序端的 `<canvas>` 在 RebornWatermark 自己的组件树里，页面作用域查不到，导出失败；又没有 `fail` 分支，`watermarkBase64` 一直是空串，背景是 `url()`，水印整块不显示，也没有任何报错。

  const { proxy } = getCurrentInstance()!

    success: (res) => { watermarkBase64.value = res.tempFilePath },

  ```
  两端都接受第二个参数，不需要条件编译。
- 影响：不改公开 API。需要在微信开发者工具和真机上各验证一次（本次只读，没有实测）。另外 `image` 传网络图片时，小程序 canvas 还要先用 `uni.getImageInfo` 下载成本地路径，属于另一处兼容问题，可以一并验证。

### [中] RebornSlider / RebornSlideVerify：touchstart 先 await 选择器查询再进入拖拽态，快速点按时 touchend 先到，拖拽态卡住
- 位置：`reborn-slider/RebornSlider.vue:548-558`（`:551` await、`:558` 置位）、`:632-633`；`reborn-slide-verify/RebornSlideVerify.vue:471-500`（`:488` await、`:493` 置位）、`:534-537`
- 类别：生命周期与清理
- 依据：reactivity.md「Clean up async effects for watchers」：异步结果回来时，要先确认它对应的那次交互还有效；SKILL.md 自检「side effects clean up with their owner」
- 现状：
  ```ts
  async function onTouchStart(e: TouchEvent) {
    if (isDisabled.value) return
    await measure()            // 小程序端要经渲染层往返一趟
    // ……
    dragging.value = true      // :558
  }
  function onTouchEnd() { if (!dragging.value) return /* …… */ } // :633
  ```
  小程序端的 `createSelectorQuery().exec` 要跨线程往返，低端机上要几十毫秒。手指在测量回来之前就抬起时，`onTouchEnd` 看到 `dragging=false` 直接返回；随后测量回来，又把 `dragging` 置为 true 并改了值。结果：Slider 的气泡和按压色晕一直显示（`thumbTooltipVisible` / `thumbPressed` 都读 `dragging`），这次点按既不发 `changeComplete`，也不触发 change 校验，直到下一次触摸才恢复。SlideVerify 同理：`isDragging` 卡在 true，发了 `start` 却没有对应的收尾，卡住期间 `refreshTrackMeasure` 一直被跳过。
- 改法：在 await 之前同步记下这次触摸；松手时如果测量还没回来，等它回来后再补走收尾：
  ```ts
  let touchSeq = 0
  let releasedSeq = -1

  async function onTouchStart(e: TouchEvent) {
    if (isDisabled.value) return
    const seq = ++touchSeq
    const touch = e.touches[0]        // 坐标在 await 之前取
    if (!touch) return
    await measure()
    if (seq !== touchSeq) return       // 期间已经开始了新的一次触摸
    // ……原有的分派逻辑（抓滑块 / 平移 / 加节点 / 就近移动）
    if (releasedSeq === seq) onTouchEnd() // 测量期间已松手：按点按处理，立即收尾
  }

  function onTouchEnd() {
    releasedSeq = touchSeq
    if (!dragging.value) return
    // ……原有逻辑
  }
  ```
  SlideVerify 不需要「点一下就生效」，松手早于测量回来时直接放弃本次拖拽即可（`if (releasedSeq === seq) return`，也不 emit `start`）。
- 影响：不改公开 API。回归：Slider 点按轨道跳值、拖拽、range 模式抓取滑块；SlideVerify 正常拖动通过与回弹。Web 端用同步的 getBoundingClientRect，没有这个问题。

### [中] RebornSlideVerify：绑定 v-model 时，success 事件载荷里的 verified 恒为 false
- 位置：`reborn-slide-verify/RebornSlideVerify.vue:330-336`（createPayload 读 `verified.value`）、`:386-394`、`:415-424`（completeVerify）
- 类别：数据流
- 依据：METHOD 项目规则「受控绑定下赋值后同步读到的仍是旧值，事件载荷要用本地新值」；component-data-flow.md「If you need the updated value immediately after a change, use the input event value」
- 现状：
  ```ts
  updateVerified(true)              // 内部执行 verified.value = true
  const payload = createPayload()   // 读 verified.value；绑定 v-model 时这里仍是 false
  emit('success', payload)
  ```
  绑定了 `v-model` 时，给 `defineModel` 赋值只会 emit `update:modelValue`，父级重渲染之前本地读到的还是旧值，所以 `@success` 收到的是 `{ verified: false }`。不绑 v-model 时是本地赋值，读到的是 true。同一个事件在两种用法下载荷不一致。
- 改法：`createPayload` 接收显式的 verified：
  ```ts
  function createPayload(verifiedValue = verified.value): SlideVerifyPayload {
    return { progress: progress.value, offset: translateX.value, verified: verifiedValue }
  }
  emit('success', createPayload(true))
  ```
- 影响：不改 API，只修正载荷字段的值。Web 端没有同名组件。

### [中] RebornSwiperAction：「值没变」的内部更新也会把 isInternalUpdate 置位，但这个标志只在 watch 里清，残留后会吞掉下一次外部 v-model 改动
- 位置：`reborn-swiper-action/RebornSwiperAction.vue:934-965`（`:943` 置位，`:955` 值相同直接返回）、`:1531`、`:1534-1562`（`:1549-1550` 消费）；以相同值调用的位置：`:1022-1029`（snapClose）、`:1034-1044`（close）、`:1274`（已打开的项回弹后保持打开）、`:1291`
- 类别：响应性
- 依据：reactivity.md「Keep state predictable」：用旁路标志区分更新来源时，标志的置位和消费必须一一对应；component-data-flow.md 中 `v-model` 的受控契约
- 现状：
  ```ts
  isInternalUpdate = true
  openedSide.value = side   // 值没变时 defineModel 既不 trigger 也不 emit，watch 不会执行
  // ……
  else if (isInternalUpdate) { isInternalUpdate = false }   // 只在 watch 里清
  ```
  关闭状态下滑一小段、没过阈值就松手（走 `snapClose()`，'' → ''），或者已打开的项被轻拖后回弹（'right' → 'right'），都会把标志留成 true。之后父级通过 v-model 主动改值（例如「全部收起」、离开页面时重置为 ''），watch 会把这次外部变更当成内部更新，跳过 `syncTranslate`，内容停在原位：状态已经关闭，视觉上还开着（反过来也一样）。
- 改法：不用一次性标志，改为记录「已经同步到位移的值」，在 watch 里比较：
  ```ts
  /** 已同步到内容位移的打开方向；undefined 表示尚未初始化 */
  let syncedSide: SwiperActionSide | '' | undefined

  function syncTranslate(side: SwiperActionSide | '') {
    syncedSide = side
    translateX.value = side === 'right' && hasRightActions.value ? -rightWidth.value : 0
  }

  watch(() => openedSide.value, (side) => {
    // 分组登记逻辑保持原样
    if (isDragging.value || side === syncedSide) return
    if (syncedSide === undefined) { syncTranslate(side); return } // 首次直接到位，不走动画
    isSmoothClosing.value = true
    syncTranslate(side)
    // ……复位定时器（见下一条）
  }, { immediate: true })
  ```
  `updateOpenedSide` 内部已经先调过 `syncTranslate(side)`，父级回写触发 watch 时值相等，自然跳过，不再需要 `isInternalUpdate` 和 `watchInitialized`。最小改法是只在 `previous !== side` 时才置位，但父级受控又不回写时标志仍会残留，所以推荐前一种。
- 影响：不改 API。回归：手势开合、点击内容收起、同组互斥、外部 v-model 开合、`rightActions` 宽度变化时的重新对齐。

### [中] RebornSwiperAction：十余处 setTimeout 不记句柄、互不取消，卸载时也不清，连续操作时旧定时器会提前清掉新一次收起的状态
- 位置：`reborn-swiper-action/RebornSwiperAction.vue:978-980`、`:998-1000`、`:1013-1016`、`:1025-1027`、`:1038-1040`、`:1284`、`:1315-1317`、`:1555-1557`（复位 isTapClosing / isSmoothClosing / isSnapping）；`:1353-1361`、`:1376-1378`（删除动画链）；卸载清理 `:1572-1578` 只覆盖 scrollLock、pageScrollWatcher、dragStartSide
- 类别：生命周期与清理
- 依据：SKILL.md 自检「side effects clean up with their owner」；composables.md「Keep related state, actions, and lifecycle cleanup together」
- 现状：
  ```ts
  function snapClose() {
    isSmoothClosing.value = true
    setTimeout(() => { isSmoothClosing.value = false }, props.closeDuration) // 没记句柄
    updateOpenedSide('')
  }
  ```
  操作区挂不挂载取决于 `shouldExposeActions`（`:216-222`，模板 `:1864` 用 `v-if`），收起动画期间靠 `isSmoothClosing` 撑着。连续两次收起时（例如 t=0 snapClose，t=100 再次触摸拖动，t=200 再次 snapClose），t=300 第一次的定时器把 `isSmoothClosing` 置成 false，第二次收起还在过渡中，操作区就被卸掉、露出底色。这正是 `:205-215` 注释想要避免的现象。删除动画链在卸载后仍会继续写 ref；父级 v-for 用下标作 key、列表在这几百毫秒内变动时，`remove` 可能发给已经换成别的数据项的实例。
- 改法：每类复位只保留一个句柄，重设前先清，卸载时统一清理：
  ```ts
  const timers = new Map<string, ReturnType<typeof setTimeout>>()

  /** 同名定时器重设前先取消，避免旧回调覆盖新状态 */
  function later(name: string, fn: () => void, ms: number) {
    clearTimeout(timers.get(name))
    timers.set(name, setTimeout(() => { timers.delete(name); fn() }, ms))
  }

  // 用法：later('smoothClosing', () => { isSmoothClosing.value = false }, props.closeDuration)
  onBeforeUnmount(() => { timers.forEach(clearTimeout); timers.clear() })
  ```
- 影响：不改 API。回归：各条开合路径的动画节奏、删除动画和 `remove` 事件的时机。

### [中] RebornSticky：吸顶触发位置只在首次测量时记录，对外暴露的 getRect() 修不了它
- 位置：`reborn-sticky/RebornSticky.vue:59-60`、`:127-161`（`:143-149`）、`:178-186`、`:189-194`
- 类别：其他（暴露方法的行为与契约不一致）
- 依据：component-data-flow.md「expose only the intended API from the child with defineExpose」：暴露的方法要做到它承诺的事；reactivity.md「Keep source state minimal」
- 现状：
  ```ts
  if (!isInitialized.value) {
    rect.left = node.left ?? 0
    rect.top = (node.top ?? 0) + scrollTop.value
    isInitialized.value = true
  }
  ```
  `isInitialized` 置为 true 之后再没复位过。sticky 上方的内容在挂载后变高（接口数据回来才渲染的 banner、加载后撑高的图片）时，触发点还是旧的 top，吸顶要么提前、要么推迟。`defineExpose` 的注释写的是「重新测量组件的位置与尺寸」，实际调用 `getRect()` 只会更新宽高。被测的是外层 `.reborn-sticky-wrapper`，吸顶时它仍留在文档流里（高度被钉住），重新量 top 本身是安全的；只锁定一次，原因应该是 `scrollTop` prop 来自节流后的 onPageScroll，测量那一刻可能与真实滚动量对不上。
- 改法：在同一个 query 里一起取视口滚动量，让 top 和 scrollTop 是同一时刻的值：
  ```ts

    uni.createSelectorQuery().in(proxy)
      .select('.reborn-sticky-wrapper').boundingClientRect()
      .selectViewport().scrollOffset()
      .exec(([node, viewport]) => {
        if (!node) return
        rect.height = node.height ?? 0
        rect.width = node.width ?? 0
        if (position) {
          rect.left = node.left ?? 0
          rect.top = (node.top ?? 0) + (viewport?.scrollTop ?? 0)
        }
      })
  }
  ```
  吸顶状态切换后的内部重测传 `{ position: false }`，保持现在的行为；暴露给外部的 `getRect()` 默认连位置一起重算。页面若是在 scroll-view 里滚动，`selectViewport` 取不到容器的滚动量，只能继续用 prop。组件支持哪几种滚动容器，要在 demo 里确认（待确认）。
- 影响：`getRect` 增加一个可选参数，向后兼容，文档 Expose 表要同步。Web 端实现机制不同，不需要同步改 API。

### [低] 模板里逐项现算样式：Slider 的间断点、Tabs 的标签、Toast 的消息，每次重渲染都重复调用 tv / cn
- 位置：`reborn-slider/RebornSlider.vue:682-699`、`:715-732`；`reborn-tabs/RebornTabs.vue:232-240`、`:619`；`reborn-toast/RebornToast.vue:162`、`:203-216`
- 类别：性能
- 依据：reactivity.md「Keep filtered/sorted derivations out of templates」「Use computed for reusable class/style logic」
- 现状：
  - Slider 拖拽时每个 touchmove 都会让整个组件重渲染。`stopValues` 最多 100 个点，加上 marks 的点和文字，每个都要调一次 `ui.stopDot()`（tv 槽函数加 tailwind-merge）和 `thumbStyle(toPct(v))`，而这些结果与拖拽值无关。
  - Tabs 的 `tabClass(pane, index)` 对每个标签、每次渲染都完整调用一次 `theme({...})`，液体底板切换一次就要写两轮 ref、渲染两次。
  - Toast 每条消息每次渲染调用 4 次 `themeOf(item)`；`classNames` / `styles` 是函数时，`semanticClass` / `semanticStyle` 每次渲染还要各调 3 次用户函数。
- 改法：抽成 computed 数组，例如
  ```ts
  /** 间断点只依赖步长与方向，拖拽时不重算 */
  const stopDots = computed(() => {
    const cls = ui.value.stopDot()
    return stopValues.value.map(v => ({ key: v, cls, style: thumbStyle(toPct(v)) }))
  })
  const tabClasses = computed(() => panes.value.map((pane, i) => tabClass(pane, i)))
  ```
  Toast 可以在 `addMessage` 时把 `themeOf` 的结果和语义类名算好挂在实例上，或者用一个按 id 缓存的 computed。不建议用 `v-memo`：uni-mp-vue 编译器是否支持没有确认。
- 影响：纯内部改动。`thumbStyle` 依赖 `props.vertical` / `reverse`，放进 computed 后照样响应。

### [低] RebornSwitch：设了 inheritAttrs: false，模板却没绑 $attrs，H5 端调用方写的 class / style / 事件监听被静默丢弃（小程序端待确认）
- 位置：`reborn-switch/RebornSwitch.vue:13`、`:195-242`
- 类别：插槽与透传
- 依据：component-fallthrough-attrs.md（透传属性的访问与转发）
- 现状：`defineOptions({ inheritAttrs: false })`，模板里没有 `v-bind="$attrs"`，也没用 useAttrs。H5 端 `<RebornSwitch class="ml-2" style="…" @click="…">` 上的这些属性不会落到任何节点上。Web 端关掉透传，是为了把 class 以外的属性转给隐藏的原生 checkbox（`inputAttrs`）；UniApp 端没有这个节点，关透传就没有理由了。小程序端组件宿主节点的 class 由编译器另外处理，是否受影响待确认。
- 改法：去掉 `inheritAttrs: false`，让 attrs 落到根 `<view>`；或者保留它，在外层 `<view>` 上写 `v-bind="$attrs"`。
- 影响：H5 端行为会变（原来被丢弃的 class / style / 监听开始生效），用到这些属性的 demo 要回归。props 不变。

### [低] RebornSwitch：异步 beforeChange 期间不加锁，连点会并发执行拦截并重复提交
- 位置：`reborn-switch/RebornSwitch.vue:158-174`；Web 端 `app/components/reborn/ui/reborn-switch/RebornSwitch.vue:225-243` 写法相同
- 类别：数据流
- 依据：reactivity.md「Clean up async effects for watchers」：同一操作的并发异步要能识别或作废
- 现状：`newChecked` 在 await 之前就按旧状态算好了。`beforeChange` 去发请求时用户连点两次，会并发执行两次拦截（两次请求或两次确认）；两次都通过后，用同一个 `newChecked` 提交两次 `update:modelValue` / `change`。
- 改法：加一个 pending 标志：
  ```ts
  let pending = false
  async function onTap() {
    if (isDisabled.value || pending) return
    pending = true
    try { /* ……原有逻辑 */ }
    finally { pending = false }
  }
  ```
  可以对照 RebornTabbar，它的 beforeChange 已经用 `locked` 防并发（`RebornTabbar.vue:328-352`）。
- 影响：不改 API。建议两端一起改。

### [低] RebornTextarea / RebornSwitch：暴露的实例 API 把可写的 ref 交给了外部，或者只置位不复位
- 位置：`reborn-textarea/RebornTextarea.vue:246-251`；`reborn-switch/RebornSwitch.vue:185-191`、`:202`
- 类别：组件边界
- 依据：component-data-flow.md「expose only the intended API from the child with defineExpose」；composables.md「Return readonly state when mutations must go through actions」
- 现状：Textarea 直接暴露了 `isFocus` ref，外部可以写它、改掉样式上的聚焦态；Switch 的 `focus()` 把 `isFocused` 置为 true 后没有任何复位路径，`is-focused` 类名会一直挂着。
- 改法：Textarea 暴露 `readonly(isFocus)`；Switch 补一个 `blur()`，或者在文档里说明这是一次性标记。
- 影响：Textarea 的 expose 类型变成只读，外部如果写过 `ref.isFocus = x` 会出类型错误（运行时写入 readonly 也会告警），文档 Expose 表要同步。

### [低] RebornTabs：provide / inject 用的是字符串键，上下文类型要靠调用方手写泛型
- 位置：`reborn-tabs/reborn-tabs.config.ts:6`；`reborn-tabs/RebornTabs.vue:576-584`；`reborn-tabs/RebornTabPane.vue:61`
- 类别：组件边界
- 依据：component-data-flow.md「In TypeScript projects, prefer type-based defineProps, defineEmits, and InjectionKey」
- 现状：`TABS_INJECTION_KEY = 'reborn-tabs'` 是普通字符串，`inject<TabsContext | null>(…)` 的泛型完全靠手写，provide 端少传或传错字段，类型检查发现不了。同分片的 RebornTabbar 已经用 `InjectionKey`（`reborn-tabbar/types.ts:33`）。
- 改法：`export const TABS_INJECTION_KEY: InjectionKey<TabsContext> = Symbol('reborn-tabs')`。
- 影响：`TABS_INJECTION_KEY` 从 index.ts 对外导出，改成 Symbol 后，外部按字符串 `inject('reborn-tabs')` 的写法会失效。Web 端 `app/components/reborn/ui/reborn-tabs/reborn-tabs.config.ts:6` 也是字符串，两端要一起改。

### [低] RebornSlideVerify：style 对象里的 Webkit 前缀用 camelCase 写，小程序端会被转成缺少前导连字符的无效属性
- 位置：`reborn-slide-verify/RebornSlideVerify.vue:243-244`、`:258`、`:265`
- 类别：模板
- 依据：sfc.md 建议 `:style` 用 camelCase 键，但 uni-mp-vue 的 `stringify` 直接对键做 `hyphenate`（`node_modules/@dcloudio/uni-mp-vue/dist/vue.runtime.esm.js:5524-5533`），`WebkitClipPath` 会变成 `webkit-clip-path`，前导 `-` 丢了。H5 端走 DOM 的 style 设置，会自动补前缀，所以两端表现不一样。
- 现状：`WebkitTouchCallout: 'none'`、`WebkitUserSelect: 'none'`、`WebkitClipPath: 'inset(…)'` 在小程序端都是无效声明，只认带前缀属性的旧内核上会失效（例如 iOS 上 `user-select` 仍需前缀）。
- 改法：带前缀的属性改用有前导连字符的 kebab 键，如 `'-webkit-clip-path': …`、`'-webkit-user-select': 'none'`。H5 端 runtime-dom 会把它 camelize 回 `WebkitClipPath`，两端都生效。反过来，`RebornTabbar.vue:142`、`RebornText.vue:145-146`、`RebornTabs.vue:314-315` 现在的 kebab 写法在小程序端是对的，不要按 sfc.md 改成 camelCase。
- 影响：只涉及样式绑定写法。

### [低] 挂载时触发了本应由用户交互引起的副作用
- 位置：`reborn-slide-verify/RebornSlideVerify.vue:573-579`；`reborn-tabbar/RebornTabbarTrigger.vue:168-177`
- 类别：生命周期与清理
- 依据：reactivity.md「Use immediate: true instead of duplicate initial calls」的另一面：初始状态应在 setup 里同步得出，不要走交互路径
- 现状：
  - SlideVerify 的 `defaultVerified` 要等 onMounted 加 nextTick 之后才调用 `updateVerified(true)`：首帧先渲染成未通过，再按 duration 过渡填满（能看到一段 220ms 的填充动画），同时在挂载时就 emit 了 `change`、`update:modelValue`，还触发了表单 change 校验。
  - TabbarTrigger 的果冻动画 watch 带了 `immediate: true`，fly-balls 模式下初始激活的那一项在页面加载时就会播放一次果冻动画（是否有意为之待确认）。
- 改法：SlideVerify 在 setup 里同步初始化：`if (props.defaultVerified && !verified.value) verified.value = true`。这样仍会 emit `update:modelValue`，让受控父级同步，但不 emit `change`、不触发校验。TabbarTrigger 的 jelly watch 去掉 `immediate`。
- 影响：SlideVerify 挂载时不再发 `change`，如果文档或业务依赖这一次 change，需要评估。Web 端两者都没有同名组件。

### [低] RebornTabbar：fly-balls 小球的颜色按子项数取模，小球比子项多时颜色错位
- 位置：`reborn-tabbar/RebornTabbar.vue:161`、`:359`、`:364`、`:379`
- 类别：其他
- 依据：SKILL.md 核心原则「one source of truth, derive everything else」：`presets` 已经派生出每个小球的颜色，渲染时却又用别的规则重算
- 现状：`backgroundColor: props.ballColors?.[ballIndex % count]`，其中 `count = children.length`；4 种颜色、3 个子项时，第 4 个球用的是第 1 个颜色。`presets` 里按小球下标算好的 `backgroundColor`（`:161`）没被用上。
- 改法：改为 `backgroundColor: p.backgroundColor`。
- 影响：只修正视觉。

### [低] reborn-toast/index.ts：H5 命令式容器在事件回调里拿不到实例，appContext 桥接实际不生效；容器挂上后还会和页面内实例重复渲染（待确认）
- 位置：`reborn-toast/index.ts:42-44`、`:57-63`；Web 端对照 `app/components/reborn/ui/reborn-toast/index.ts:40-45`（有 useNuxtApp 兜底）
- 类别：组件边界
- 依据：component-data-flow.md 中 provide/inject 作用域的要求；Vue 规定 `getCurrentInstance()` 只在 setup 和生命周期钩子同步执行期间有值
- 现状：注释说「命令式调用大多发生在事件回调里，桥接当前应用上下文」，但在事件回调里 `getCurrentInstance()` 恒为 null，`vnode.appContext` 实际上从没被赋值过，容器里拿不到 app 级的 provide 和全局组件。RebornToast 目前没用到这些，所以还没表现出来。另外，`:42` 只在第一次挂容器前检查页面里有没有实例；容器一旦挂上就常驻，之后进入带 `RebornPage`（内置 RebornToast）的页面时，两个实例渲染同一份 `messageState.list`，同一位置叠两层（需要在 H5 上确认视觉）。
- 改法：提供一个一次性的 `installMessage(app)` 记下 appContext（在 main.ts 里调用），或者由页面实例在 `markMessageMounted` 时上报 appContext；页面实例挂载时如果容器存在，就让容器不再渲染列表（例如 messageState 里记录「当前渲染者」）。
- 影响：可能新增一个导出函数。只涉及 H5，小程序端没有影响。
