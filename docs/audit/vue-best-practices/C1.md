### [高] useOverlay：浮层登记在模块级 Map 里，`create()` 不随调用方作用域注销，组件每挂载一次就永久多出若干条记录，打开着的浮层也会比创建它的组件活得更久
- 位置：
  - `app/composables/useOverlay.ts:68`（模块级 `overlayStates`）
  - `app/composables/useOverlay.ts:172-203`（`create` 只 `set`，不登记任何清理）
  - `app/composables/useOverlay.ts:265-268`（只有 `destroyOnClose` 才在关闭时 `delete`）
  - `app/composables/useOverlay.ts:311-334`（只有调用方手动 `unmount(id)` 才移除）
  - 调用方：`app/components/reborn/examples/reborn-dialog/RebornDialogDemo.vue:214-283`（一次 setup 建 10 个实例，第 217-219 行把演练场的响应式 `state.value` 整个交给 `props`）、`app/components/examples/UseOverlayDemo.vue:6-23`
- 类别：生命周期与清理 / SSR
- 依据：
  - `references/composables.md`「Keep related state, actions, and lifecycle cleanup together」「Create shared state once per intended scope」。
  - `SKILL.md` 自检项「State has explicit ownership and lifetime ... side effects clean up with their owner」。
- 现状：
  ```ts
  // useOverlay.ts:68
  const overlayStates = new Map<symbol, OverlayState>();
  // useOverlay.ts:188（create 内）
  overlayStates.set(id, state);
  ```
  文档与 demo 的标准写法是在组件 setup 里 `overlay.create(...)`。这个调用把状态写进模块级 Map，但没有任何东西把它和调用方的作用域绑在一起：
  1. **客户端泄漏**：每进入一次 Dialog 文档页，`RebornDialogDemo` 就新增 10 条记录，离开页面后一条不删。记录里有组件引用、props 对象（第一条直接是演练场的响应式 `state`，把已卸载 demo 的状态图一起钉在内存里），以及 `content` / `header` / `footer` 闭包（会捕获调用方 setup 作用域）。来回切页，记录只增不减。
  2. **孤儿浮层**：浮层打开期间如果创建它的组件卸载（例如用浏览器后退离开页面），独立应用仍挂在 `body` 上，弹窗和它持有的滚动锁都留在新页面里，只能靠用户手动关闭。
  3. **SSR**：`create()` 不碰 `document`，在服务端也能执行。本仓库的 demo 外层套了 `ClientOnly`（`ComponentViewer.vue:29`），所以眼下服务端不会走到；但这是 CLI 分发给使用方的组合式函数，使用方在普通 SSR 页面的 setup 里调用 `create()` 时，每个请求都往服务端进程的同一个 Map 里写记录，跨请求共享、永不释放。
- 改法：
  - `create()` 里检测当前作用域，随作用域注销：
    ```ts
    import { getCurrentScope, onScopeDispose } from 'vue';

    const create = <T extends Component>(component: T, options?: OverlayOptions<T>) => {
      // 服务端不登记：open() 依赖 document，登记了也用不上，只会跨请求堆积
      if (typeof document === 'undefined') return createNoopInstance<T>();
      const id = Symbol('overlay');
      // ……原有登记逻辑……
      // 在组件 / effectScope 内创建时，随作用域一起卸载并移出登记表
      if (getCurrentScope()) onScopeDispose(() => unmount(id));
      return instance;
    };
    ```
  - 若想保留「跨组件共享同一个实例」的用法，再加一个显式选项（例如 `persistent: true`）跳过自动注销，默认值仍是随作用域。
- 影响：
  - 不改 `create` 的签名；行为变化是「创建者卸载时浮层随之关闭并移出登记表」，`open()` 的 Promise 会以 `undefined` 解析（走 `close`）。
  - 要同步 `content/4.composables/use-overlay.md`（第 15 行「所有实例登记在模块级的状态表里」）与 `.agents/skills/reborn-web/references/composables-overlay.md`。UniApp 端没有 useOverlay，不涉及。
  - 回归：`tests/composables/use-overlay.test.ts`、Dialog 文档页全部 overlay 示例、`UseOverlayDemo`。

- 位置：

  - `app/composables/useOverlay.ts:165-166`（`createApp(WrapperComponent).mount(...)`）

- 类别：组件边界 / 其他（无障碍）
- 依据：
  - `references/component-data-flow.md`「Provide/Inject：Place the provider at the nearest common ancestor ... match its lifetime to the intended scope」：独立应用拿不到任何祖先 `provide`。
  - `references/component-teleport.md`：需要脱离当前 DOM 位置时用 `Teleport` 留在同一棵组件树里，而不是另起应用。
- 现状：
  ```ts
  // useOverlay.ts:165
  state.app = createApp(WrapperComponent);
  state.app.mount(state.container);
  ```
  已对照本仓库的 Vue 3.5.29 核实：`useId()` 返回 `(appContext.config.idPrefix || "v") + "-" + ids[0] + ids[1]++`，根组件的 `ids` 初值是 `['', 0, 0]`，子组件沿用父级数组（`runtime-core.cjs.prod.js:1218-1224`、`6322`）。每个浮层应用都从零计数，所以浮层里的 `RebornDialog` 拿到的永远是 `reborn-dialog-title-v-0` / `reborn-dialog-description-v-1`：
  1. 两个 overlay 浮层同时打开（浮层内容里再 `open()` 另一个），页面上出现两个同 id 的标题节点，第二个弹窗的 `aria-labelledby` / `aria-describedby` 指到第一个弹窗。主应用里排在异步边界之前的组件也可能生成同样的 `v-0`，同样会撞。

  - **推荐**：改成宿主组件方案（与 Nuxt UI 的 `OverlayProvider` 同构）。登记表换成客户端共享的 `shallowReactive` 列表，在 `app.vue` 放一个 `<RebornOverlayHost>`，用 `v-for` 渲染所有浮层，并以 `Teleport to="body"` 输出。浮层留在主组件树里，`useId`、`provide`、全局组件、错误处理全部自然继承。这个方案也一并解决下一条的「重挂载」和「无离场动画」。
  - **最小修补**：保留 `createApp`，给每个浮层应用设唯一前缀，并接上主应用的错误处理：
    ```ts
    const nuxtApp = useNuxtApp(); // 在 useOverlay() 调用时取一次
    let overlaySeq = 0;           // 模块级计数，只在客户端递增
    // mountOverlay 内
    state.app = createApp(WrapperComponent);
    state.app.config.idPrefix = `rb-overlay-${++overlaySeq}`;
    state.app.config.errorHandler = nuxtApp.vueApp.config.errorHandler;
    ```
- 影响：
  - 推荐方案要在 `app.vue` 增加宿主组件，并改写 `use-overlay.md` 的「独立的 Vue 应用」「关闭是立即卸载」两条注意事项。
  - `create` / `open` / `close` / `patch` 的签名不变。
  - 最小修补不改任何行为，只改 id 前缀与错误上报。
  - `useLoading`（`useLoading.ts:287-288`）用的是同一种 `createApp` 写法，但 `RebornLoadingMask` 不调用 `useId`，也不依赖上下文，目前没有可见后果，不单列；若采用宿主方案，可以一并迁移。

- 位置：

  - `app/composables/useOverlay.ts:123-124`（`modelValue` 固定为 `true`）

  - `app/composables/useOverlay.ts:296-305`（`patch`：卸载后重新 `mountOverlay`）
- 类别：响应性 / 生命周期与清理
- 依据：
  - `references/reactivity.md`：状态要有唯一来源，更新应改数据而不是重建视图。
  - `references/component-transition.md`：离场动画需要元素在 `leave` 期间仍然存在，直接卸载宿主会跳过离场。
- 现状：
  ```ts

  const reactiveProps = ref(state.currentProps);
  // useOverlay.ts:228（已打开时只改了 state.currentProps，组件看不到）
  if (!state.app) { mountOverlay(state, id); }
  ```
  三个可观察的后果（`use-overlay.md` 第 142-146 行都作为注意事项写了，说明是已知限制，不是有意设计）：
  1. 打开状态下 `patch()` 会重建整个组件：输入到一半的表单、滚动位置、焦点全部丢失，入场动画也会再播一遍（`RebornDialog.vue:831-832` 的 `RebornTransition` 带 `appear`）。
  2. 任何关闭路径（取消、确认成功、点遮罩、`close()`）都同步卸载应用，`RebornDialog` / `RebornDrawer` 的离场过渡和 `closed` 事件都不会触发。Dialog 文档里「延迟打开 / 关闭」示例（`RebornDialogDemo.vue:252-262` 的 `closeDelay: 500`）在这个模式下也看不到关闭延迟。
  3. 已打开时再 `open(newProps)`：新 props 不生效，`state.resolve` 被覆盖，之前 `await open()` 的调用方永远等不到结果。
- 改法：
  - 把 `reactiveProps` 和一个 `visible` 都提到 `OverlayState` 上，用 `shallowRef` 存；渲染时 `modelValue: visible.value`。
  - `patch()` 直接 `state.propsRef.value = { ...state.propsRef.value, ...props }`，不再重挂。
  - `close()` 先 `visible.value = false`、解析 Promise，等组件发出 `closed`（两个组件都已有该事件）后再卸载，并照 `useLoading.ts:340` 加一个兜底定时器。
  - `open()` 遇到已打开的实例时，先以 `undefined` 解析旧 Promise，再更新 props。
  - 采用上一条的宿主组件方案时，这些都是自然结果。
- 影响：
  - API 签名不变。行为变化：`patch` 不再丢失内部状态，关闭有离场动画，`open()` 的解析时机不变（关闭即解析，不等动画）。
  - 要同步改写 `use-overlay.md` 第 142-146 行的三条注意事项。
  - 回归：`tests/composables/use-overlay.test.ts`、确认流程（`onConfirm` loading）、`UseOverlayDemo` 的 `patch`。

### [中] useLockScroll（UniApp H5）：锁计数器按实例创建，嵌套弹层关掉内层就把页面滚动解锁了；`watch` 没有 `immediate`，以打开状态挂载的弹层不上锁
- 位置：

  - `packages/uniapp-project/src/composables/useLockScroll.ts:50-51`（`onDeactivated` 解锁，没有对应的 `onActivated` 重新上锁）

- 类别：生命周期与清理
- 依据：
  - `references/composables.md`「Create shared state once per intended scope」：页面滚动锁是页面级资源，计数要全局共享，不能每个调用方各一份。
  - `references/reactivity.md`「Use `immediate: true` instead of duplicate initial calls」：初始状态也要走一遍副作用。
  - Web 端 `app/composables/useGlobalScrollLock.ts:8-17` 的注释记录了同一个根因（「一方释放时会把另一方仍需要的锁一并解开」），并已改成模块级计数。
- 现状：
  ```ts
  export function useLockScroll(shouldLock: () => boolean) {
    const scrollLockCount = ref(0)            // 每个遮罩各自一份
    const lock = () => { if (scrollLockCount.value === 0) { body.style.overflow = 'hidden'; applyOverscrollLock() } ... }
    watch(shouldLock, (value) => { value ? lock() : unlock() })
  ```
  1. **嵌套弹层提前解锁**：弹层 A 打开后在里面再打开弹层 B（例如 Popup 里的选择器再弹一层）。两个实例的计数都从 0 → 1，B 关闭时它自己的计数归零，执行 `body.style.overflow = ''`，A 还开着，背景页面已经可以滚动。另外 `applyOverscrollLock` 第二次执行时把 `dataset.rbOverscrollPrev` 覆盖成了 `'none'`，保存的原值被冲掉。
  2. **初始即打开不上锁**：遮罩挂载时 `modelValue` 已为 `true`（父级用 `v-if` 渲染一个默认打开的弹层），watch 不会触发，页面不锁；卸载时 `destroy` 的 `unlock` 因计数为 0 也什么都不做。
  3. **KeepAlive**：失活时解锁，再激活时不重新上锁。
- 改法：照 Web 端 `useGlobalScrollLock` 的做法，计数提到模块级（UniApp H5 是纯客户端，没有 SSR 跨请求问题），每个调用方只持有一个「我是否持锁」的标记：
  ```ts
  let lockCount = 0   // 模块级：所有遮罩共用

  export function useLockScroll(shouldLock: () => boolean) {
    let holding = false
    const lock = () => {
      if (holding) return
      holding = true
      if (lockCount++ === 0) { document.body.style.overflow = 'hidden'; applyOverscrollLock() }
    }
    const unlock = () => {
      if (!holding) return
      holding = false
      if (--lockCount === 0) { document.body.style.overflow = ''; restoreOverscrollLock() }
    }
    watch(shouldLock, value => (value ? lock() : unlock()), { immediate: true })
    onActivated(() => { if (shouldLock()) lock() })
    onDeactivated(unlock)
    onBeforeUnmount(unlock)
    return { lock, unlock }
  }
  ```
- 影响：
  - 不改组件 API，只有 `RebornOverlay` 一处调用。所有基于遮罩的 UniApp 弹层（Popup、ActionSheet 等）都会受益。
  - 回归：H5 下单层 / 嵌套弹层的打开与关闭、页面切换后 `body` 的样式残留。
  - 小程序端不编译这段代码，不受影响。

### [低] useChildren（UniApp）：`unlink` 没判断下标为 -1，会误删最后一个子项；组件内部实例被放进深层 `reactive` 数组
- 位置：`packages/uniapp-project/src/composables/useChildren.ts:80-81`（`reactive([])` 存 `ComponentInternalInstance`）、`93-97`（`unlink`）；调用方 `packages/uniapp-project/src/components/reborn-tabbar/RebornTabbar.vue:81`、`RebornTabbarTrigger.vue:49`
- 类别：响应性 / 其他
- 依据：`references/reactivity.md`「Use `shallowRef()` / `shallowReactive()` when the value is opaque / should not be proxied (class instances, external library objects ...)」。
- 现状：
  ```ts
  const unlink = (child) => {
    const index = internalChildren.indexOf(child)
    publicChildren.splice(index, 1)    // index 为 -1 时删掉的是数组最后一项
    internalChildren.splice(index, 1)
  }
  ```
  `link` 只在 `child.proxy` 存在时才登记。没登记过的子组件（或同一实例被注销两次）卸载时，`indexOf` 得 -1，`splice(-1, 1)` 会把最后一个兄弟子项删掉，之后它的 `index` 变成 -1，失去激活态。另外 `ComponentInternalInstance` 没有被 `markRaw`，放进 `reactive` 数组后，经由数组读出的都是深层代理，`sortChildren` 读 `vnode`、`subTree` 时会沿途创建代理。这是 vant 原版写法，有效但多余。
- 改法：`unlink` 先判断 `if (index < 0) return`；两个数组改为 `shallowReactive([])`，排序与 `indexOf` 的结果不变。
- 影响：纯内部改动，Web 端无对应实现；回归 Tabbar 动态增删项。

### [低] useCopyToClipboard：写入失败没有处理，产生未捕获的 Promise 拒绝，用户也收不到任何反馈
