### [高] RebornBackTop：按钮隐藏后仍占位并响应点击，点到就回顶并抛出 click
- 位置：`packages/uniapp-project/src/components/reborn-back-top/reborn-back-top.config.ts:6`、`packages/uniapp-project/src/components/reborn-back-top/RebornBackTop.vue:78`、`:96-102`、`:105`
- 类别：模板
- 依据：`references/sfc.md`「Choose v-if vs v-show by toggle behavior」——不可见的状态不应继续参与交互；`SKILL.md`「Keep state predictable」
- 现状：可见性只体现在 `opacity`，点击处理不看 `visible`；wrapper 上写的 `pointer-none` 不是有效的 tailwind 类（全仓库没有定义），所以 wrapper 一直能命中点击：
  ```vue
  <view :class="ui.wrapper()" :style="{ bottom: viewBottom, opacity: visible ? 1 : 0 }" @tap.stop="toTop">
  ```
  `visible === false` 时，按钮原位（屏幕右下角一块 wrapper 区域）是透明的，但点上去会 `uni.pageScrollTo({ scrollTop: 0 })` 并 `emit('click')`，同时 `.stop` 吞掉事件，盖在下面的列表项、Fab 等收不到点击。首页 `packages/uniapp-project/src/pages/index/index.vue:185` 写的是 `<RebornBackTop />`，没传 `scroll-top`，`visible` 恒为 false，这块透明热区始终存在。
- 改法：两处一起改。
  1. 处理函数先判可见：`function toTop() { if (!visible.value) return; ... }`；
  2. 隐藏时让 wrapper 不接收点击：配置里把 `pointer-none` 改成 `pointer-events-none`，并在模板上按状态补回：
     ```vue
     <view :class="ui.wrapper({ class: visible ? 'pointer-events-auto' : '' })" ...>
     ```
     （`pointer-events` 小程序端支持；保留 opacity 过渡，不改成 v-if。）
- 影响：不改公开 API。行为变化：隐藏时点击穿透到下层。Web 端同名组件实现不同，无需同步。回归点：默认插槽替换按钮时也要能在可见态点击。

### [高] RebornCollapse：点击触发区只改内部 isOpened，不回写 v-model，受控状态与界面脱节
- 位置：`packages/uniapp-project/src/components/reborn-collapse/RebornCollapse.vue:24-27`、`:37`、`:44-55`、`:79-85`、`:88-98`、`:110-113`
- 类别：数据流
- 依据：`references/component-data-flow.md`「v-model: Predictable Two-Way Bindings」「Use defineModel for v-model」；`references/reactivity.md`「keep source state minimal, derive everything possible」
- 现状：同一个开合状态有两份来源：`collapse`（defineModel）和 `isOpened`（本地 ref）。模板与插槽读 `isOpened`，点击走 `toggle()` 只改 `isOpened`：
  ```ts
  function toggle() {
    if (isOpened.value) { hide() } else { show() }   // 不写 collapse
  }
  watch(() => collapse.value, (val) => { val ? show() : hide() }, { immediate: true })
  ```
  触发条件：使用方写 `v-model="visible"` 再点触发区（演示页 `packages/uniapp-project/src/pages/reborn-collapse/RebornCollapseDemo.vue:22` 正是这种用法）。展开后父级 `visible` 仍为 false；此时父级再把 `visible` 设为 false，值没变、watch 不触发，面板关不上；父级依赖 `visible` 的其他 UI 也与面板不一致。
- 改法：以 model 为唯一来源，`isOpened` 改为派生；开合的副作用（测高）放在 watch 里：
  ```ts
  const isOpened = computed(() => collapse.value)
  function show() { collapse.value = true }
  function hide() { collapse.value = false }
  function toggle() { collapse.value = !collapse.value }
  watch(collapse, (val) => { if (val) updateHeight(); else height.value = 0 }, { immediate: true })
  ```
  未绑定 v-model 时 defineModel 自动退化为本地状态，非受控用法不受影响。
- 影响：不改 props / slots / expose 签名。Web 端 `app/components/reborn/ui/reborn-collapse/RebornCollapse.vue` 已是「直接改 model」的写法，并多了 `disabled` 与 `toggle` 事件；本端若顺手补齐，属于新增 API，需同步文档与知识库。

### [高] RebornColorPickerPanel：输入框每敲一个字就被规整成完整颜色写回，手动编辑颜色文本无法进行；watch 派生值回写还让程序化赋值也触发 onChange
- 位置：`packages/uniapp-project/src/components/reborn-color-picker/RebornColorPickerPanel.vue:106-122`、`:125-141`、`:149-151`、`:277`；`packages/uniapp-project/src/components/reborn-color-picker/RebornColorPicker.vue:98-103`、`:121-122`
- 类别：数据流
- 依据：`references/reactivity.md`「Keep computed getters pure… put side effects in watchers」与「Prefer computed over watcher-assigned derived refs」；`references/component-data-flow.md`「Emits: Explicit Events Up」（事件应来自用户操作，而不是派生值的变化）
- 现状：
  1. 文本框直接 `v-model` 到可写 computed，setter 每次输入都提交到 `colorHsv`：
     ```ts
     set: (val: string) => { colorHsv.value = colorStringToHsva(val) ... }
     ```
     `colorStringToHsva` 解析失败不抛错而是返回黑色（`packages/uniapp-project/src/lib/color-utils.ts:127-134`，`hexToRgba` 位数不对返回 `{0,0,0,1}`），所以 `try/catch` 永远走不到。用户把 `#FF0000` 删掉一位变成 `#FF000`，getter 立刻变成 `#000000`，RebornInput 的 `:value` 随之被改写，输入框跳成黑色；逐字键入 `rgb(` 同理。只有整段粘贴合法值才能用。
  2. `watch(displayValue, val => emit('update:modelValue', val))` 把派生值的任何变化都当成用户操作往外发。父级改 `v-model`（如重置表单）→ Panel 的 modelValue watcher 改 `colorHsv` → `displayValue` 变 → 回发 `update:modelValue` → `RebornColorPicker.onPanelChange` 再 `emit('onChange', value)`，文档写的「用户在面板中选色导致颜色变化时触发」被程序化赋值触发；同时 hex 大小写在两层之间被改写一轮。
- 改法：
  - 输入框改用本地草稿：`const draft = shallowRef('')`，未聚焦时跟随 `displayValue`；`@update:model-value` 里先用 `parseColorString` 判断，能解析才提交到 `colorHsv`，解析失败只更新草稿；失焦 / confirm 时若仍非法则回滚为 `displayValue`。
  - 去掉 `watch(displayValue)`，改为在真正的用户操作处显式提交：抽一个 `commit()`（`emit('update:modelValue', 当前文本)`），在饱和度/色相/透明度的触摸回调、`selectPreset`、格式切换、草稿合法提交时调用。modelValue watcher 只同步内部状态，不再触发 emit。
- 影响：不改公开 API。`onChange` 的触发时机收窄到用户操作，与文档描述一致；需回归：拖动色板、点预设、切格式、手输 hex / rgb / rgba 四种路径的 v-model 值。Web 端 Panel 是否有同样的 setter 提交写法需在 W 分片另行核对。

### [高] RebornFab：items 动作项同时绑定 @tap 与 @click，一次点击 action 事件触发两次
- 位置：`packages/uniapp-project/src/components/reborn-fab/RebornFab.vue:439-443`（对照 `:291-303`、`:452-454`）
- 类别：模板
- 依据：`references/component-data-flow.md`「Emits: Explicit Events Up」（一次用户操作对应一次事件）；uni-app 编译规则（见文首）
- 现状：
  ```vue
  <view v-for="(item, index) in items" ... @tap.stop="onActionItemTap(item, index)" @click.stop="onActionItemTap(item, index)">
  ```
  H5 端 `@tap` 在编译期被改写成 `@click`，同一节点上出现两个 click 监听，Vue 把它们合并成数组依次执行；`.stop` 只阻止冒泡，不阻止同节点的另一个监听，所以 `onActionItemTap` 每次点击执行两次，`action` 事件抛两次。小程序端 `@click` 又被改写回 `tap`，两条绑定指向同一事件，同样存在双发风险。主按钮那一路靠 `activateTrigger` 里 45ms 的时间窗去重（注释已承认「tap / click 可能短时间双发」），动作项这一路没有去重。使用方在 `@action` 里做跳转、计数、提交时会执行两遍。
- 改法：每个节点只保留一个点击绑定。`@tap.stop` 在 H5 会变成 click、在小程序就是 tap，单独一条即可覆盖两端：删掉动作项上的 `@click.stop`；主按钮同样只留 `@tap.stop="activateTrigger"`，随后可去掉 45ms 去重逻辑。
- 影响：不改公开 API；`action` 事件改为每次点击只触发一次，属于修 bug。回归点：H5、微信小程序各点一次动作项，确认只收到一次 `action`；主按钮展开 / 收起不受影响。

### [高] RebornDraggable：根节点 @touchmove.stop.prevent 无条件拦截，手指落在列表上时页面无法滚动
- 位置：`packages/uniapp-project/src/components/reborn-draggable/RebornDraggable.vue:2-4`、`:61`、`:141-150`、`:592-595`、`:740-753`
- 类别：模板
- 依据：`references/sfc.md`「Keep templates declarative」；Vue `withModifiers` 的 `prevent` 守卫在调用处理函数前无条件执行 `e.preventDefault()`；uni-app 小程序端 `.stop` / `.prevent` 编译为 `catch:`（见文首）
- 现状：
  ```vue
  <view class="reborn-draggable" ... @touchmove.stop.prevent="dragWxs.touchmove">
  ```
  组件本意是「只在拖拽中阻止滚动」：H5 有 `h5PreventScroll` 只在 `dragging` 时 `preventDefault`，wxs 也只在 `data-dragging` 为真时 `return false`。但根节点上的 `.prevent` 让 H5 对每一次冒泡到根节点的 touchmove 都调用 `preventDefault`，与是否拖拽无关；小程序端 `.stop.prevent` 编译成 `catch:touchmove`，同样一律拦截。结果：默认 `longPress` 模式下，用户在列表区域上滑动想滚动页面，页面不动；列表较长时下半部分无法滚到。另外 `<script setup>` 里声明了同名桩对象 `const dragWxs = { touchmove: () => true }`（`:61`），模板里的 `dragWxs.touchmove` 在各端究竟解析到 wxs 模块还是这个桩，**待确认**。
- 改法：去掉根节点的 `.stop.prevent`，让「是否阻止」由运行时状态决定：
  - 小程序 / App：`@touchmove="dragWxs.touchmove"`（普通 bind，wxs 在拖拽中 `return false` 即可阻止滚动与冒泡）；
  - H5：依赖已有的 `document.addEventListener('touchmove', h5PreventScroll, { passive: false })`，它只在 `dragging` 时生效。必要时把两种写法用 `// #ifdef H5` / `// #ifndef H5` 分开。
  - 桩对象改名或改成类型声明（如在 `env.d.ts` 里声明模块类型），避免与 wxs 模块同名。
  - **待确认**：H5 上在列表区域上下滑动能否滚动页面（预期当前不能）；微信小程序真机上去掉 catch 后，拖拽中页面是否仍被 wxs 正确锁住。
- 影响：不改公开 API。行为变化：非拖拽时允许页面滚动，文档「注意事项」可补一句。回归点：H5 与小程序上长按拖拽、拖拽中页面不跟随滚动。
