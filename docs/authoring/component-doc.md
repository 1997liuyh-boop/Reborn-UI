# 组件文档写作规范

**唯一参考范本：`content/2.components/button/reborn-button.md`。** 本文是从该范本逆向提炼的规范，两者冲突时以范本为准。写新文档时的最佳做法是：先读范本，再按本文逐条自检。

适用范围：`content/2.components/**/*.md`（Docus 内容站的组件文档）。demo 文件（`app/components/reborn/examples/**`、`packages/uniapp-project/src/pages/**`）的结构规范见 `component-demo` skill，其文案规范与本文同源。

---

## 0. 三条最容易违反的硬规则

先记住这三条，其余细节可以边写边查：

1. **章节骨架固定且有序**，见 §1。缺 `## 简介` / `### 何时使用` / `## 注意事项` 的文档一律视为不合规。
2. **`## API` 下的表格行名必须与源码成员逐字一致**，CI 强校验，编名字直接挂。见 §7。
3. **不描述源码里不存在的能力。** 预留未接线的 prop 要在 `## 注意事项` 里明说「当前是预留 prop」，不能默认它能用。见 §10。

---

## 1. 章节骨架

固定顺序，标题层级与写法照抄：

```
---
frontmatter（见 §2）
---

::ComponentViewer{...}          ← §3
::

## 简介                          ← §4（三段制）

### 何时使用                     ← §5
### 何时不使用                   ← §5

## 用法                          ← §6
### <能力名>                     ← 一节一能力，若干节
...

## API                           ← §7
### Props
### Emits
### Slots
### Expose                       ← 有暴露实例方法时才写
### 自定义样式（ui）              ← §8
### CSS 变量                     ← §8

## 两端差异对照                   ← §9，仅双端组件
## 注意事项                       ← §10
```

允许的缺节，且只有这几种：

| 缺哪节 | 允许条件 |
| --- | --- |
| `## 两端差异对照` | 单端组件（只有 web 或只有 uniapp 实现） |
| `### Expose` | 组件没有 `defineExpose` |
| `### Emits` / `### Slots` | 组件确实没有事件 / 插槽（不要写空表占位） |
| `### CSS 变量` | 组件不消费专属 CSS 变量（只用通用色板不算） |

**不允许**为了省事跳过 `## 简介` / `### 何时使用` / `### 何时不使用` / `## 注意事项`——这四节是 Agent 选型与避坑的主要信息来源，也是本规范存在的理由。

## 2. frontmatter

```yaml
---
title: 按钮
description: 双端基础按钮：7 种语义色 × 7 种变体，支持尺寸、形状、加载与禁用状态。
category: 按钮
tags: [css, tailwind, button, uniapp]
badge: New
navigation:
  badges:
    - label: 通用
      color: primary
  chip:
    label: NEW
    color: primary
---
```

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `title` | 是 | 不带「组件」二字（写「按钮」不写「按钮组件」）。优先纯中文名（「按钮」「徽章」）；组件以英文名更为人知时写「English 中文」（「Form 表单」「PickerView 选择器视图」）。**不要只写英文**。 |
| `description` | 是 | 一句话 ≤60 字。见下方专条。 |
| `category` | 是 | 与目录分类一致。 |
| `tags` | 是 | 小写英文，含技术栈与组件名；双端组件必须带 `uniapp`。 |
| `badge` / `navigation` | 否 | 新组件可加 `badge: New`；`navigation.badges` 标注适用端或分组。 |

### `description` 是 Agent 选型的第一依据

这一句同时是知识库 `description` 的真源：`kb:build` 直接取 frontmatter 的 `description`（见 `scripts/kb/merge.ts`），所以规则与 `knowledge/README.md` 的「描述规范」完全同一条、同一批禁词，写好这里就不必再写第二遍（只有 `knowledge/overrides/<id>.json` 显式写了 `description` 才会分叉，那种情况下两处措辞要保持一致）。

- **≤60 字，一句话。** 写清「是什么 + 关键可区分维度」。
- **必须含区分性信息。** 「7 种语义色 × 7 种变体」能把它和别的按钮区分开；「基础按钮组件」不能。
- **禁营销词**：优雅、强大、时尚、炫酷、极致、完美。
- **禁「xxx 属性」式废话**：写实际语义（含单位、取值范围、联动行为），不写「用于设置 size 的属性」。

反例 → 正例：

```
✗ description: 一个优雅强大的按钮组件，支持丰富的自定义配置。
✓ description: 双端基础按钮：7 种语义色 × 7 种变体，支持尺寸、形状、加载与禁用状态。
```

## 3. ComponentViewer

紧跟 frontmatter：

```mdc
::ComponentViewer{demoFile="RebornButtonDemo.vue" config="RebornButtonConfig" componentId="reborn-button" :componentFiles='[]' :uniappFiles='[]'}
::
```

`componentId` 必须与「组件源码目录名 / registry 条目 `name` / 文档文件名 / `knowledge/components/<id>.json`」四处完全一致（kebab-case）。这条约定见 `AGENTS.md`。

**viewer 之前只允许放一件东西**：单端组件的适用端提示，一个 `::warning`（或 `::tip`）块，一句话说清「仅 X 端」并给出另一端的替代组件。这是有意允许的——读者应当在看 demo 之前就知道它在自己的端上能不能用：

```mdc
::warning
仅 UniApp 端组件。Web 端表单选值请使用 `reborn-select`，操作菜单请使用 `reborn-dropdown`。
::
```

除此之外，**frontmatter 与 viewer 之间不允许出现标题或正文**。把 `## 基础用法` 或组件介绍写在 viewer 上方会打乱骨架（`## 简介` 之前不该有 `##` 级标题），正文里也不要再写 `#` 一级标题——页面标题来自 frontmatter 的 `title`。

## 4. `## 简介` 三段制

三个自然段，各自承担不同职责，不要合并也不要多写：

**① 一句话定位 + 双端同名同构声明。** 说明它是什么、解决什么，并交代两端是否同名同构、API 是否对齐。

**② 正交维度拆解。** 这是简介里信息密度最高的一段：把组件的核心 API 拆成互相独立的轴，说明「A 决定什么、B 决定什么、A×B 覆盖什么梯度」。范本的写法：

> `color` 决定语义（primary / secondary / success / info / warning / error / neutral），`variant` 决定视觉强度（filled / outlined / soft / subtle / text / round / circle），两轴自由组合覆盖从主行动到辅助链接的完整梯度。

没有正交维度的组件（比如只有一个 `items` 数据源），这段改写为「数据驱动方式 + 渲染契约」，同样要说清输入与产出的关系。

**③ 剩余 API 分组概览。** 把余下的 props/events 按 形状 / 尺寸 / 状态 / 插槽 / 端特有能力 分组，一句一组。让读者读完简介就知道 API 面有多大、分几类。

## 5. `### 何时使用` / `### 何时不使用`

这两节是给选型用的，不是给鉴赏用的。

**`### 何时使用`：3-5 条，每条必须点名具体 prop。**

```
✓ - 页面主行动（提交、保存、下一步）——用 `color="primary"` + `variant="filled"`。
✗ - 需要用户点击的场景。
```

**`### 何时不使用`：2-3 条，每条必须给出替代组件。** 格式是「场景描述 —— 改用 `xxx`」。这与知识库 `whenNotToUse` 尽量给替代组件 id 的要求同源。

```
✓ - 悬浮在内容之上的圆形主操作 —— 改用 `reborn-fab`。
✗ - 不适合复杂交互的场景。
```

替代方案不是本库组件时同样要写具体：指向原生能力（「等高条目的规则网格 —— 直接用 CSS grid」）或平台 API 都算合格；实在没有替代就写「本库暂无替代，需自行实现」。唯一不允许的是含糊其辞（「不适合复杂场景」）。

## 6. `## 用法`

### 一节一能力

每个 `###` 子节只讲一个能力维度，节名用能力名而不是 prop 名（写「加载与禁用」而不是「loading 属性」）。范本的节序可直接沿用：基础用法 → 颜色与变体 → 尺寸 → 形状 → 状态 → 插槽 → 布局 → 与其他组件联动 → 端特有能力。

### 每节的内部结构

1. **一句话引子**，prop / 事件名用反引号包裹，说清它控制什么、默认值是什么、与其他 prop 有无联动。
2. **可枚举的维度上表。** 只要取值是有限集合就必须上表，列头形如 `变体 | 外观 | 典型用途`——第三列「典型用途」是关键，它把「有什么」变成「什么时候用哪个」。
3. **可运行的 `vue` 代码块，5-15 行。** 只保留与本节能力相关的代码；需要状态时写完整的 `<script setup lang="ts">`。不要贴整页 demo。

### 旁注块的分工

| 语法 | 用途 |
| --- | --- |
| `::tip` | 机制性解释：为什么这样实现、有什么副作用。 |
| `::warning` | 端限制、平台资质要求、会导致功能失效的前提条件。 |

### 双端差异的表达

对齐的内容不拆端，直接写正文（必要时点明「两端通用」）。**只有真正不对齐的部分才拆 tabs**，拆分粒度是**单张表 / 单个代码块**，不要把整节复制两份：

```mdc
::tabs{sync="platform"}

:::tabs-item{label="Web" icon="tabler:world"}
三档，高度固定 px：

| `size` | 高度 | 字号 |
| --- | --- | --- |
| `sm` | 24px | 12px |
:::

:::tabs-item{label="UniApp" icon="tabler:brand-wechat"}
七档，高度用 `rpx` 随屏宽缩放：

| `size` | 高度 | 字号 |
| --- | --- | --- |
| `xs` | 48rpx | 22rpx |
:::

::
```

`label` / `icon` 两个属性照抄，不要自创图标名。判断「是否对齐」必须**回源码对比**，不能沿用旧文档里的表述——旧表可能已经过时。

## 7. `## API`（CI 强校验）

**这一节有硬约束，写错会让 CI 失败：**

- `### Props` / `### Emits` / `### Slots` / `### Expose` 标题下**必须**包含表格行，且每行第一列的成员名必须与源码里的实际成员**逐字一致**。凭印象编一个不存在的 prop 名 → CI 直接报错。
- 反过来，**`ui` 键位表和 CSS 变量表不能放在这四个标题下**，否则会被当作 props/slots 校验而报错。它们要放在非 API 标题下：`### 自定义样式（ui）`、`### CSS 变量`。

表格列头统一：

| 类型 | 列头 |
| --- | --- |
| Props | `属性名 \| 类型 \| 默认值 \| 描述` |
| Emits | `事件名 \| 回调参数 \| 描述` |
| Slots | `插槽名 \| 作用域参数 \| 描述` |
| Expose | `方法名 \| 签名 \| 描述` |

写法要求：

- **枚举型 prop 的类型列写完整字面量联合**，不要偷懒写 `string`：`` `'sm' \| 'md' \| 'lg'` ``。表格里的 `|` 必须转义成 `\|`。对象型 prop（如 `ui`）写实际类型或 `Record<string, string>`，不要写 `any`。
- **默认值列**写真实默认值，无默认写 `-`。
- **描述列写语义与联动**，含单位与取值范围，并交代与其他 prop 的相互作用（「处于表单组内时被组尺寸覆盖」）。禁止「设置尺寸的属性」这类同义反复。
- 双端 props 不一致时用 `::tabs{sync="platform"}` 拆，tab 内加 `#### Web 端全部属性` / `#### UniApp 端全部属性` 四级标题。**每个 tab 列全量属性**，不要只列差异——读者在某一端时看到的应当是那一端的完整清单。

## 8. `### 自定义样式（ui）` 与 `### CSS 变量`

**`### 自定义样式（ui）`**：先一句话说明 `ui` 的作用（按内部结构键覆盖对应节点类名），再上 `键名 | 说明` 表。说明里要写清默认类名和**失效条件**——范本的 `label` 键是最好的例子：

> `label`：文本节点，默认 `truncate leading-none`。**仅在使用 `label` prop 时渲染**，填充 default 插槽会替换掉该节点，`ui.label` 随之失效——需要保留该样式时在插槽里用作用域的 `:class="ui.label()"`。

两端 DOM 结构不同时用 tabs 分列键位。末尾给一个 `:ui="{...}"` 的代码块。

**`### CSS 变量`**：必须写出**定义文件的仓库路径**（`app/assets/theme/typography.css` / `packages/uniapp-project/src/styles/theme.css`），再上 `变量名 | 对应取值 | 值` 表。UniApp 端要提醒变量挂在 `:root, body, page` 上、覆盖时需对齐同一选择器。

## 9. `## 两端差异对照`

仅双端组件需要。一张 `维度 | Web | UniApp` 三列表，把全文散落的差异集中成一份速查清单——读者不必通读全文就能判断迁移成本。

必查维度（有差异才写，无差异不写）：自定义类名入口、尺寸档位、形状 API、圆角、内边距、边框、布局 prop、`ui` 键位、动画尺寸、表单组联动、点击态、端特有能力。

这节只做**索引**，不展开解释；解释留在 `## 用法` 对应小节。

## 10. `## 注意事项`

每条一行，格式固定：**粗体结论句** + 句号 + 机制 + 后果 / 应对。

```
✓ - **`loading` 隐含禁用**。加载中按钮不会派发 `click` / `tap`，无需再额外绑 `disabled`。
✗ - 使用 loading 时请注意按钮状态。
```

必须披露以下三类真相，有就写，不要藏：

**① 有意偏离。** 与常见实现或另一端不一致，且是刻意的：

> **形状并入 `variant`**。两端都没有 `round` / `circle` 布尔 props……默认 `filled` 不再是胶囊，而是随 `size` 取 4 / 6 / 8 的圆角令牌；需要自定义圆角时直接用 `class` / `customClass` 覆盖。

**② 预留但未接线的 prop。** 源码里声明了、实际没生效的，必须明说，否则就是在制造幻觉：

> **`fluid` 当前是预留 prop**。UniApp 端已声明但尚未接入样式，需要等宽填充请改用 `block` 或外层 flex 布局。

**③ 反直觉实现。** 看起来像 bug、其实是预期行为的：

> **`text` 变体不占固定高度**。它用 `!h-auto !px-0` 覆盖了 `size` 的高度与水平内边距，与其他变体并排时基线不齐是预期行为；需要对齐请把它放进同一个 flex 容器并用 `items-center`。

条数参考：范本 7 条。少于 3 条通常意味着漏挖，多于 10 条说明该拆进 `## 用法`。

## 11. 文风

- **给理由不给口号。** 每个结论后面跟机制或后果。「`text` 变体不占高度」后面必须跟「因为 `!h-auto !px-0` 覆盖了 size」。
- **一律中文。** 代码标识符、类型字面量、文件路径除外。
- **禁营销词。** 优雅、强大、时尚、炫酷、极致、完美，一个都不要。
- **不写源码里不存在的能力。** 拿不准就去读源码或 `reborn-*.config.ts`，不要按同类库的印象推断。
- **数值必带单位并区分端**：Web 用 px，UniApp 用 rpx，不要混写。

## 12. 收尾清单

改完 `content/2.components/**` 的文档后：

1. 若改动了 API 表格、`whenToUse` / `whenNotToUse` / 注意事项的事实内容，重建该组件的知识条目：

   ```bash
   pnpm kb:build --only <componentId>
   ```

2. 校验知识库一致性（CI 同样会跑）：

   ```bash
   pnpm kb:check
   ```

3. 起文档站确认 MDC 语法渲染正常（`::tabs` 未闭合、`:::tabs-item` 层级写错都会让整节塌掉）。

不要手改 `knowledge/components/*.json`、`knowledge/index.json`——它们由 `kb:build` 生成。需要覆盖描述时改 `knowledge/overrides/<id>.json`。
